# Instant start: landing order

File one item per numbered slice, in order. The first builds a view without giving it any authority to start work. There is only one handoff of that authority, in slice 16. The improvement can ship there; slice 17 is optional follow-up. This division is the designer's proposal on the operator's request; the owner may overturn it. The owner's dated words and verify's result are in [What to split and how to judge it](../design/tillr-judge-and-lifecycle.md#what-to-split-and-how-to-judge-it).

## What counts as a result

On 2026-11-20 at 4:15 PM ET, verify measured **filing to start, excluding staging: 2.4–3.6 s before, 406–752 ms after**. That compares the common ancestor with the *whole verified candidate*. It is neither a measurement of today's trunk nor a target for each piece.

For every item, measure its parent and its candidate on the same workload: make independent copies of the same store snapshot, `git init` disposable roots with equivalent refs and documents, start the same loop configuration and file the same ready request with a free lane. Time filing to the recorded start claim, before worktree staging. Report both revisions, fixture size, trial count and observed times with units. Never point a measurement loop at the live store or a checkout sharing the project Git directory; clear `TILLR_LOOP_STORE`. Repeat the comparison from the pre-series base at the handoff. Report a neutral preparatory slice as neutral; investigate regressions. The acceptance evidence is the before/after result, **not a fixed millisecond threshold**. The tests below prove ordering and correctness without racing a stopwatch.
