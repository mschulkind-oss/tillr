# The Item Judge and Lifecycle in Tillr

> **Delivered copy.** This is `docs/design/tillr-judge-and-lifecycle.md` from this repository at commit `e613f54fde` (2026-11-24), copied into the tillr pack by `just pack-docs`. The [source](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-judge-and-lifecycle.md) is authoritative and may be newer. Links to documents that were not delivered point at the repository, and the queue item directives in this copy are inert.

**Status:** in review. Four ledger rows ([OQ-JL1](#OQ-JL1), [OQ-JL2](#OQ-JL2), [OQ-JL4](#OQ-JL4) and `D-JL8`) are designer's decisions the owner has not ruled on; each row says so. The Built column of the [decision ledger](#decision-ledger) says what is in the code. One question is open, [OQ-JL5](#OQ-JL5).

> **In short.** A criterion is retired only by an actor with authority over its class, and an item's stored state says what its owner wants done with it, never what a run is doing. Everything a run does short of landing is evidence returned to whoever can act on it: it neither retires a criterion nor spends a retry budget. Repeated verifier findings can, however, put an open item on hold for triage.

**Why it matters.** Without these rules a gate pass retires a decision only the owner can make, and a failed attempt freezes criteria nobody has judged. A judge needs no grantor: it is a step of the workflow ([Section 6](#6-the-judge-is-a-step-in-the-flow)).

**The shape.** One verdict intake shared by every judge; a claim class stored on each criterion and checked against the actor; six stored item states with `working` derived from live runs; and, for every way a run can end, one named mover.

**Cost.** There is no `autoqa` actor kind, no stored `in-progress` state, no clone of a held item under a new id, and no `tillr drain rework` command.

**Start at [Section 4](#4-a-failed-attempt-is-never-a-verdict-and-never-a-count)**, which carries the owner's rulings on run endings, held lanes, leftover work in lanes taken out of rotation, same-item lane continuation, fork delivery, live trunk fixers, bounded run IDs and per-item staging holds, and instant start decisions from a background-maintained queue view.

**Needs your ruling:** [OQ-JL5](#OQ-JL5): does a worker's `seat` obstacle still move the item to a stronger model?

**Reads with:** [tillr-item-graphs.md](../reference/tillr-item-graphs.md) (the graph and evaluator contract this judges inside), [the graph design](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-graph-is-the-path.md#33-endings) (the closed set of next actors an objection may name), [the item-states reference](../reference/tillr-item-states.md) (the seven displayed states), [criterion-repair.md](criterion-repair.md) (repairing a criterion a verdict has frozen), and [tillr-autoqa.md](tillr-autoqa.md) (the external client of [Section 5](#5-core-boundary-for-external-autoqa-d-jl7)).

**Words.** This document uses the names the built code uses. [The vocabulary](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-vocabulary.md#5-the-words) defines item, criterion, fence, gate, candidate, judge, seat, backend, objection and mover. It also replaces two words the code and this document still say: a *lane* is a pool slot holding one worktree and one run, and a *hold* is a wait together with the mover that ends it. Four more are used here:

- **Worker**: the run that builds an item's change.
- **Design seat**: the role that answers a question about an item's definition by editing the item's block or its design document. A **design run** is one agent run in that seat. It is not the worker and never builds the item.
- **Objection**: the ending by which a run says it should not continue and names who acts next.
- **Operator**: whoever runs tillr's commands at a shell. It is not a seat, and not an actor a run's report can name.

## 1. The Defects This Design Closes

| Defect | Cause | Closed by |
| :--- | :--- | :--- |
| **A gate pass retires an owner's decision.** A loop that stamps every criterion of an item `done` when the gate passes lets a five-second Markdown check retire a criterion reading "Owner decision recorded". | A claim class that lives only on the incoming verdict lets a mechanical actor claim `verification-only` for any criterion. | The class is stored on the criterion and checked against the actor ([Section 2.2](#22-when-generic-judging-survives--and-closing-the-mechanical-stamp-hole-d-jl2)). Built. |
| **A failed attempt makes an item unrepairable.** If every candidate that does not land writes `not-done` against each criterion, the criterion's text freezes before any judge has read it, and the only way round is a clone of the item under a new id. | An attempt's outcome recorded as a criterion verdict. | An attempt writes no verdict ([Section 4.1](#41-attempt-outcomes-are-not-criterion-verdicts-d-jl5)), and a held item is never cloned ([Section 4.2](#42-sending-a-failed-item-again-under-its-own-id-d-jl6-d-jl8)). Built. |
| **A client signs off without the check other agents pass.** A store-level `autoqa` actor kind skips the independence check every other agent passes. | A client's identity encoded as an authority kind. | No such kind exists; a client is named in the verdict's `actor` field ([Section 5](#5-core-boundary-for-external-autoqa-d-jl7)). Built. |

## 2. The Judge Runs Before the Gate, and Its Verdicts Are Recorded After the Landing

### 2.1 Topology Relative to Gate and Land (`D-JL1`)

Per [tillr-item-graphs.md](../reference/tillr-item-graphs.md) ([graph exit and evaluator routing](../reference/tillr-item-graphs.md#graph-exit-and-evaluator-routing), [lane lifecycle](../reference/tillr-item-graphs.md#lane-lifecycle-write-scopes-and-chained-commits), `D-IG8`, `D-IG9`), intra-graph landing is forbidden and `Loop.Verify` runs at most once at root graph exit. In any pre-approved graph carrying an `evaluator_slot` (such as `build-judged@v1` or `design-draft@v1`), the judge leaf sits **topologically after all `access: "write"` leaves and any in-graph preflight `check` leaves, and strictly before root `exit` and `Loop.Verify` (`tillr-gate` -> `tillr-land pass`)**:

```
[write leaves: edit, pack-sync] ──► [optional check leaf (command, read_only)]
                                              │
                                              ▼
                                    [evaluator_slot leaf (agent, read_only)]
                                              │ emits .tillr/loop/<run_id>/artifacts/eval.output
                     ┌────────────────────────┴────────────────────────┐
          outcome == "fail"                                  outcome == "pass" (all criteria `done`)
    (not-done | blocked | defective)                                   │
                     │                                                 ▼
                     ▼                                       Serial `Loop.Verify`
     Settlement Hook (NO Gate, NO Land;                      1. Common deny-list (requested)
     `main` untouched; lane reset)                           2. `tillr-gate` (`gate.verdict`)
       • `not-done`  -> `in-queue` (held `eval-failed`,      3. `tillr-land pass` (fast-forward or carry)
                        `item_criteria` untouched)           4. Settlement Hook commits `done`
       • `blocked`   -> `blocked` (`waiting_on` set,            `item.verdict` records (citing landed sha
                        `item_criteria` untouched)              + `gate.verdict`) -> `SetState(landed)`
       • `defective` -> `item.verdict(defective)` +
                        `Close(item, "defective: ...")`
```

**Why pre-land evaluation paired with post-land verdict commit is mandatory:**
- Running the judge **before** `Loop.Verify` catches spec drift, unaddressed clauses, and `defective` premises in the scratch lane worktree before `tillr-gate` spends full suite wall time and before `tillr-land pass` moves `main`.
- Committing `done` `item.verdict` rows to `.tillr/state.db` **only after `tillr-land pass` succeeds** prevents an item reading as complete before it lands. If `tillr-gate` fails or `tillr-land pass` isolates on a carry conflict after the judge passed, **zero** `item.verdict` rows are written, the item stays `in-queue`, and the refusal goes back to the worker ([Section 4.4](#44-how-a-worker-runs-ending-moves-its-item-d-jl10)). When `tillr-land pass` carries (`Reapply`) onto an advanced `main`, `tillr-land` has already verified tree/patch equivalence (`D-UT18`), so the settlement hook binds both `evaluated_head` (candidate sha) and `landed: [<trunk_after>]` onto each `done` `item.verdict`.

**Judge leaf output contract and deterministic settlement intake.** Lanes never open `.tillr/state.db` directly. The `evaluator_slot` leaf (`role: "evaluator"`, `access: "read_only"`) writes `.tillr/loop/<run_id>/artifacts/eval.output` validated by `tillr-drain`'s settlement hook before calling `RecordVerdict`:

| `eval.output` / intake field | Requirement enforced by `tillr-drain` + `RecordVerdict` |
| :--- | :--- |
| **`evaluated_head` & `evaluated_tree`** | Must match `Candidate.HeadSHA` and `Candidate.HeadSHA^{tree}` (or `item_base_sha` when `requires_candidate == "no_commit"`). |
| **`verdicts[]` completeness** | Exactly one entry per stored criterion of `item_id`, each carrying `criterion_id`, `criterion_hash == CriterionHash(frozen_text)`, `verdict` in `{done, not-done, blocked, defective}`, `claim_class`, non-empty `reason`, and non-empty `evidence[]` (artifact/diff/commit locators, never prose-only). |
| **Provenance-stamped `actor` & `judged_actor`** | Never trusted from model output. `tillr-drain` stamps `actor = "<evaluator_node_id>:<evaluator_run_id>:<evaluator_route>"` and `judged_actor = "<writer_run_ids>:<writer_routes>"` from W1's `node_runs` table ([tillr-item-graphs.md](../reference/tillr-item-graphs.md#workflow-evaluator)), refusing any shared `run_id` or session handle (`checkIndependence`; [OQ-JL2](#decision-ledger)). |
| **Workflow rulebook** | The selected judging step and its declared classes constrain agent verdicts; the stored criterion class and independence checks still apply ([Section 6](#6-the-judge-is-a-step-in-the-flow)). A new verdict that cites `grant_id` is refused (`grant-retired`). |
| **Multi-criterion aggregation** | `outcome == "pass"` iff **every** criterion is `done` (any claim of `"pass"` with a non-`done` entry is refused as malformed intake). On `"fail"`, precedence is: any `defective` -> record `defective` verdict(s) and `Close` item (`close_reason: "defective: <id>: <reason>"`); else any `blocked` -> move item to `blocked` with structured `waiting_on` from the judge's blocker payload; else (`not-done`) -> keep item `in-queue` held as `eval-failed` with `eval.output` indexed on the run. |

### 2.2 When Generic Judging Survives — and Closing the Mechanical-Stamp Hole (`D-JL2`)

The in-graph and generic routes partition without duplicate judge passes, and any agent judge is a step of the selected workflow ([Section 6](#6-the-judge-is-a-step-in-the-flow)):

1. **Pre-approved graph with `evaluator_slot != nil` (`build-judged@v1`, `design-draft@v1`):** No generic judge runs after `Gate`/`Land`. The pre-exit `evaluator_slot` leaf already judged the criteria; `Gate` + `Land` verify and publish the tree, and the settlement hook commits the pre-exit `done` verdicts.
2. **Graph with `evaluator_slot == nil` (`single-worker@v1`) and pure `verification-only` criteria:** By default ([OQ-JL1](#decision-ledger)), `Gate` + `Land` exit `0` triggers mechanical retirement (`actor_kind: "mechanical"`, `claim_class: "verification-only"`, citing `gate.verdict` + `land.land`) at zero judge token spend.
3. **Opt-in and non-pipeline generic judging (same `evaluator` role, outside the build graph):** Generic judging survives as a standalone read-only `evaluator` invocation over the **exact same `eval.output` intake contract** — never a second codebase and never an automatic Pi turn-end hook — in four cases:
   - legacy `single-worker@v1` items carrying `judge_mode: "agent"`, translated to an explicit workflow judge under [Section 6](#6-the-judge-is-a-step-in-the-flow); a non-mechanical criterion alone does not select a judge;
   - foreground or out-of-band commits on `main` (`tillr item judge --item <id>`), where no drain pipeline landing occurred;
   - pre-dispatch premise triage (`requires_candidate: "no_commit"`) to retire a stale item as `defective` without running a worker; and
   - post-hoc audit sampling of mechanically retired items.

**A mechanical actor cannot retire an `owner-only` or `direction` criterion.** Three rules hold that:

1. **The class is stored on the criterion.** `item_criteria.claim_class` defaults to `verification-only` and is declared in the item's own block with the attribute `claims` (`D-JL8`). It may harden (`verification-only` to `red-gate-triage` or `direction`, and any of them to `owner-only`) per [criterion-repair.md](criterion-repair.md) [§1](criterion-repair.md#1-the-invariant-the-freeze-protects) `P1`, and is never weakened through `item apply`.
2. **The store checks the actor against the class.** `RecordVerdict` reads the criterion's text and stored class, refuses a verdict that claims a different class (`claim-class-mismatch`), and checks the actor's authority before writing:

   | Stored `item_criteria.claim_class` | `actor_kind: mechanical` | `actor_kind: agent` | `actor_kind: human` |
   | :--- | :--- | :--- | :--- |
   | `verification-only` | **Allowed** (with `gate.verdict` + commit receipt) | **Allowed** with independence and the judging step's class | **Allowed** |
   | `red-gate-triage` | **Refused** (`claim-class-actor`) | **Allowed only if** the judging step explicitly names it, with independence | **Allowed** |
   | `direction` | **Refused** (`claim-class-actor`) | **Allowed only if** the judging step explicitly names it, with independence | **Allowed** |
   | `owner-only` | **Refused** (`claim-class-actor`) | **Refused** (`claim-class-actor`) | **Allowed** (sole writer) |


3. **Untyped owner prose is refused, and an item that owes an owner's ruling is held.** `Apply` refuses a `verification-only` criterion whose text begins "Owner decision recorded" (`owner-criterion-untyped`), and rows of that kind already in a store were typed by one migration (`D-JL8`). The planner holds any `in-queue` item with an unretired `owner-only` criterion as `owner-only-owed`, so that an item which cannot finish without the owner spends no lane. That hold is [the second block](#hold-an-item-that-still-owes-an-owners-ruling) of the build order.

## 3. The Owner-Disposition State Machine and Derived Execution State

### 3.1 Stored Owner Disposition vs Derived Execution Projection (`D-JL3`)

An item's stored state says what its owner wants done with it. Whether a run is working on it is derived, never stored.

- **Six stored states.** `not-started` (a draft, not admitted), `in-queue` (admitted to dispatch), `blocked` (waiting on a named waiter, with the state it was in remembered), `landed` (this item's work is on the trunk), `resolved-elsewhere` (its intent was satisfied by another path) and `closed` (taken out of work with a reason, and reopenable). The legacy `abandoned` and `deleted` stay readable and cannot be written.
- **`in-progress` cannot be written.** The store refuses it with the rule `state-frozen`. A row that still holds it is read as queued.
- **One projector.** `ProjectItemState` in `tools/tillr-view` emits the seven displayed states of [the item-states reference](../reference/tillr-item-states.md). It answers `working` only for an item that is unfinished, unblocked and has a running run, and the header's dispatchable count is the planner's own rule, so the page and `tillr drain plan` cannot disagree.

### 3.2 Transition Preconditions and Attempt Holds (`D-JL4`)

Every move between stored states has a precondition the store checks, and a refusal names its rule.

| Move | Allowed from | Precondition (rule on refusal) | Built |
| :--- | :--- | :--- | :--- |
| to `in-progress` | none | Always refused (`state-frozen`). | ✅ |
| to `blocked` | `not-started`, `in-queue`, `blocked` | A waiter and a reason (`blocked-waiter-missing`). The waiter is `owner`, `design`, `plan` or `item:<id>` for a stored item (`blocked-waiter-invalid`). The prior state is remembered so that unblocking restores it. | ✅ |
| to `landed` | `not-started`, `in-queue`, `blocked` | At least one criterion and every criterion `done` (`landed-criteria-unmet`), and a current `landed` landing record or `drain.graph-completed` event naming the item (`landed-receipt-missing`). | ✅ |
| to `resolved-elsewhere` | `not-started`, `in-queue`, `blocked` | A pointer to what resolved it: `item:<id>` for another stored item, `commit:<sha>` or `doc:<path>` (`resolved-pointer-missing`). Refused when the item already has a current receipt (`already-landed`). | ✅ |
| out of `landed` or `resolved-elsewhere` | `landed` | Refused (`state-terminal`) except the return of a reverted landing to `in-queue` via `state` with reason and actor. | ✅ |
| to `closed` | `not-started`, `in-queue`, `blocked` | A reason (`close-reason-missing`). Refused while the item has a current landing receipt (`already-landed`): an unreverted landing wins. The lander refuses a candidate for a `closed` or `resolved-elsewhere` item (`item-not-landable`). | ✅ (`D-JL23` below states the close guard) |
| out of `closed` | `closed` | Only by the reopen command, with a reason, which restores the state the item was closed from. A plain state write is refused (`closed-use-reopen`). | ✅ |

A receipt is current only if it follows the latest return from `landed` to `in-queue`, or the item has never returned.

**Rework after a revert (`D-JL23`).** Designer's decision on the operator's request; the owner may overturn it. An item returned to `in-queue` after a revert keeps its durable landed row as the record of the original run. That row neither bars a close after the return nor makes the item finished for pin cleanup: the [ref sweep](../../tillr-drain/drain/refs.go) applies the ordinary retryable-item retention rules until the item settles again. An unreverted landing still refuses close. The end-to-end case is: land an item, revert and return it, sweep while its new candidate still needs the pin, then judge, gate and land that candidate under the same item ID without operator intervention.

**A failed run never changes the stored state.** `in-queue` says the item is wanted. It does not say what the last run did, and the planner derives that on every pass from the store's records, with a reason and a mover for each. The reasons are one table, `tools/tillr-drain/holdrules/holdrules.go`, which a test keeps complete: `returned-with-evidence`, `gate-failed`, `candidate-no-op`, `eval-failed`, `run-unjudged`, `retry-unjudged`, `run-infra-exhausted`, `backend-closed`, `question-open` and `judge-defective` are the ones this design touches. None of them is a count, and none expires. Under [`D-JL13`](#46-a-held-item-never-occupies-a-lane-d-jl13), no held item occupies a lane while it waits: any unlanded work in its lane is saved under a drain-owned ref recorded on the item, and the lane returns to rotation in the same pass. Under [`D-JL14`](#47-offered-commits-own-candidate-lanes-unlaunched-claims-and-named-hold-movers-d-jl14), every hold reason and the `retryHoldReason` fallthrough (`tools/tillr-drain/drain/plan.go`) names what was found and a concrete mover rather than `"cause not recorded"`.

## 4. A Failed Attempt Is Neither a Verdict nor a Charge Against a Retry Budget

### 4.1 Attempt Outcomes Are Not Criterion Verdicts (`D-JL5`)

A criterion's text freezes once a verdict is recorded against it, so that nobody lowers a bar a judge has already graded. An attempt that did not land is not such a grading, so it writes no criterion verdict and leaves the text editable.

| How the attempt ended | What is recorded | Where the item goes |
| :--- | :--- | :--- |
| The worker names a complete obstacle | The obstacle, on the run | The route of its kind ([Section 4.5](#45-what-a-worker-may-end-with-d-jl11)) |
| No commit, `RESULT: failed`, or an incomplete obstacle | A missing output, on the run | Back to the same worker session ([Section 4.4](#44-how-a-worker-runs-ending-moves-its-item-d-jl10), ending 1) |
| The candidate touches protected state, the gate refuses it, or the lander refuses it | A `drain.refusal` event with the evidence | Back to the worker with the evidence (ending 1) |
| The landing conflicts | The conflicting paths | Back to the producer on the latest trunk, restarted fresh from the current trunk on the second identical conflict, and parked for the operator if that fresh attempt conflicts again (ending 1a) |
| A judge finds a criterion `not-done` | The judge's file, on the run | A workflow's evaluator returns it to the workflow (ending 1b). Any other judge leaves the item waiting as `eval-failed` |
| A judge finds a criterion `blocked` | The judge's waiter and reason | The item moves to `blocked`, waiting on that waiter |
| The run was killed or interrupted | Nothing against the item | It is run again (ending 5) |

Two endings do write a criterion verdict, because they are gradings: `done`, recorded only after the landing succeeds, and `defective`, a judge's finding that the criterion's premise is false, which is recorded and closes the item with the judge's reason. The planner then shows the closed item as `judge-defective`. [Criterion repair](criterion-repair.md) is the design for what happens to its frozen text.

### 4.2 Sending a Failed Item Again Under Its Own Id (`D-JL6`, `D-JL8`)

A failed item is always worked again under the id it has. Its run history and its place in other items' dependencies stay with it.

- **Returned by the loop.** A refused or empty run goes back to its worker with the evidence, without a command or a retry limit ([Section 4.4](#44-how-a-worker-runs-ending-moves-its-item-d-jl10)).
- **Returned by a person.** `tillr drain retry` is the one explicit command. No `tillr drain rework` command exists: a second command for the same act would be a second place to be wrong (`D-JL8`).
- **Never cloned.** `tillr item sync` refuses a copy of a held item filed under a new id. `resolved-elsewhere` therefore means only this: the intent was satisfied by another path.

### 4.3 How a Design Run's Ending Moves Its Conflict (`D-JL9`)

When a worker reports `RESULT: blocked`, the drain records a design conflict and dispatches one design-seat run to answer it. Owner ruling, 2026-11-17: the drain does not count that run's endings. **Rule: no numeric threshold applies to design runs, and nothing is re-dispatched because something changed. An item reaches the owner only through an explicit objection that names the owner. Each ending does the one thing it means:**

| Ending | What moves the conflict | Built |
| :--- | :--- | :--- |
| 1. The gate refuses the design run's commit (for example the `documents` lint) | The failing checks and output return to the **same designer session**, even when the refusal is identical. The next turn has a new run record for its own pre-gate check, gate, and landing. A refusal the trunk caused is the gate's to recognize, not a reason to re-run the designer on a file-change guess. | Built. |
| 2. The run committed an answer to the item's block | The settlement reads the block by its id and section. No guard or count is kept around it. | Built. |
| 3. The run was killed or interrupted (a loop stop, a lease reclaimed after its loop died, a signal) | The drain continues the recorded session when available; otherwise the conflict explains why it starts a fresh one. Nothing is counted. | Built. |
| 4. The run committed, but not to the item's block | The design seat did what it judged right. No check asks whether the commit amended the block: a design commit that passes the gate and lands is the answer, and the item goes back to its worker. A commit that removes or renames the block leaves no item to build, so it goes back to the design seat naming the commit. | Built. |
| 5. The run committed nothing | A legitimate objection. Its report names the next actor with a line `NEXT-ACTOR: <actor>`, and policy routes on it: `build` (the worker was wrong; build as written) answers the conflict and returns the item to its worker; `owner` (a ruling only the owner can make) holds it for the owner. A run that commits nothing and names no actor, even one whose report ends blocked, is a missing output rather than an objection: it goes back to the design seat, told the contract, and never defaults to the owner. | Built for `build` and `owner`, which is the whole set ([OQ-JL4](#OQ-JL4) in the ledger). An objection naming the owner is published as a numbered question in the item's design document, where the owner answers it ([Owner decisions in documents](../../tillr-drain/README.md#owner-decisions-in-documents)). |
| 6. The run "ran out of time" | There are no timeouts: a budget is a target, never a cause of failure. No backend policy in `config/tillr/` sets `timeout_seconds`, so no run has a wall. A run labeled `timed-out` with the end cause `lease-reclaimed` is one whose claim a replacement loop reclaimed after its own loop died, stamping the reclaim time as the finish. That label is a mislabel, not a limit; such a run is a killed run (ending 3). | Nothing to build. The label is reported, not changed. |
| 7. The ending is not a gate refusal and repeats an earlier design ending of the item exactly: the same cause and the same evidence, such as a second run that names no actor for the same conflict and the same block | Returning it to the design seat would send the design seat the same thing again, and the design seat is already the seat that diagnoses; each further round is a paid design run. The loop raises an objection naming the owner, with a question written from the two records, and nothing is counted. The objection is recorded the way a design run's own `NEXT-ACTOR: owner` is: a `conflict-owner` hold whose conflict text carries the question and the command that moves it. Two different endings are never a repeat, however many there are. | Built, including the question's publication in the design document. |

The owner also ruled out every re-dispatch on a guessed change. A metadata write, a prose rewrite or any edit to the item's block is not a reason to spend a design run, so the drain does not compare the block, the design document or the trunk to raise a design conflict, and an item built on the design seat is not re-admitted on a changed input. The explicit operator command, `tillr drain retry --item <id> --run <design run>`, stays: it is explicit. An owner's answer to an objection is the event that moves the item to the actor the answer implies. The answer is the ruling recorded on the published question, read from the trunk at the next sync.

An identical repeat (ending 7) is the comparison [`D-JL10`](#44-how-a-worker-runs-ending-moves-its-item-d-jl10) uses on the worker path, the same pure function over the design seat's records. An ending's evidence key is its cause plus its evidence:

- **No actor named, or the block removed:** the conflict and a digest of the item's block on the trunk when the ending is settled, which is the block the next design run would be given.
- **A deny-list refusal or a refused landing:** the refusal's own words.

An interrupted or killed run has no key and never repeats. The objection's mover is the owner, not the design seat: the next actor on a design-seat repeat cannot be the seat that just produced the same ending twice. The owner moves it by changing what the design seat is given and running `tillr drain retry --item <id> --run <the later design run>`, or by closing the item.

The drain README's section [A design run that ends without answering](../../tillr-drain/README.md#a-design-run-that-ends-without-answering) states the built rule and its tests.

**Provenance rule in every design-seat brief (`D-JL19`, designer's decision from an operator request).** A brief that tells a design run to make "the recorded decision match the request" without the standing provenance rule ([`OQ-PR22`](https://github.com/mschulkind-oss/tillr/blob/main/docs/tillr/decision-provenance-review.md#OQ-PR22) and [Section 6 of the decision provenance review](https://github.com/mschulkind-oss/tillr/blob/main/docs/tillr/decision-provenance-review.md#6-how-this-stops-happening)) invites the run to present an operator request and its own mechanism as the owner's ruling. So every brief staged for the `design` seat (single-worker design items, `design` workflow nodes, and conflict or triage dispatches, in [`stage.go`](../../tillr-drain/drain/stage.go), [`plain_stage.go`](../../tillr-drain/drain/plain_stage.go) and `requestObstacleDesignInstruction` in [`obstacle.go`](../../tillr-drain/drain/obstacle.go), pinned by [`brief_seats_test.go`](../../tillr-drain/drain/brief_seats_test.go)) states the rule directly: a designer's or operator's decision — including a filed request and any mechanism, format, field names, or rejected alternatives the design seat writes — is never presented as the owner's ruling; prose and Decision Ledger rows may say the owner ruled or attribute a decision to `owner` only when quoting a dated ruling of the owner's in his own words, and otherwise mark the decision as the designer's (or from an operator request) that the owner may overturn.

### 4.4 How a Worker Run's Ending Moves Its Item (`D-JL10`)

The owner's ruling of 2026-11-17 covers the worker seat too, the run that builds an item rather than designs it. **Rule: a worker's ending never spends a retry budget, and nothing re-runs because a hash changed. Each ending does the one thing it means, and an identical repeat goes to the design seat:**

| Ending | What moves the item | Built |
| :--- | :--- | :--- |
| 1. The gate refuses the candidate, the run commits nothing, the candidate touches protected state, or the landing is refused | The ending goes back to the item's worker with its evidence, without a retry limit. The next turn continues the same worker session on the retained lane when the adapter can resume it, with a distinct run record and the refusal's own words, each failing gate check with its log, and the refs that keep the earlier run's work. A workflow continues its producing node with the original boundaries and accepted inputs. An unavailable session, unsupported adapter, changed seat or unavailable lane starts a fresh run with that evidence and a recorded reason. | Built. |
| 2. An identical repeat: the same producer, the same cause and the same evidence as any earlier ending of the item (except `squash-conflict` and `verify-not-done`, which follow endings 1a and 1b) | The item goes to the design seat with both runs' records. Two endings that differ are never a repeat, however many there are. The evidence is the sorted ids of the failing checks with a digest of each check's normalized output, or the uncommitted paths with a digest of their content, or the refusal's normalized words. Normalizing drops the run id, timestamps, durations, full hashes and temporary directories. | Built. |
| 1a. The landing conflicts (`squash-conflict`) | Before any conflict restart in the current retry cycle, a conflict goes back to the producer with the conflicting paths on the latest trunk: at once as a conflict-fix run with the three-way markers when the trunk moved under the candidate, and otherwise as the next pass's returned run. On the second identical conflict within the current retry cycle — the same conflicting paths and normalized hunks digest as an earlier conflict ending since the latest `tillr drain retry` — the drain discards the candidate (clearing any replayed dirty or repair holds on it and closing any open landing call on it), resets the lane to the current trunk, and returns the item so the planner starts a fresh attempt of its workflow from the first stage on the current trunk (`D-JL12`). That fresh attempt's brief carries the item's normal source reference (`body_ref` or saved request words) with no conflict-fix instructions, states that the earlier attempt conflicted twice at landing, and names the conflicting paths. If that fresh attempt conflicts again at landing, the item parks for the operator (`WaitingOn: "owner"`, `conflict-owner`) regardless of whether the conflicting paths or hunks changed and regardless of whether the item has a document block or a mapped `design` seat. | Built. |
| 1b. A workflow evaluator finds a criterion `not-done` | The refusal `verify-not-done` returns the unanswered findings, criterion IDs and complete reasons to the worker. Only a repeated finding on unchanged candidate evidence holds for the operator (see below). The non-workflow `eval-failed` route is unchanged. | Built. |
| 3. The run exits with uncommitted work in its checkout | Its session is continued, for as long as each continuation changes that work. A continuation that leaves the work as the previous one did is refused as `candidate-no-op` (ending 1), and a repeat of that refusal is ending 2. | Built. |
| 4. The run reports `RESULT: blocked` | Since [`D-JL11`](#45-what-a-worker-may-end-with-d-jl11), it must name a complete obstacle, and each obstacle kind has its own route. A blocked report without one is a missing output: ending 1, run that committed nothing. | Built. |
| 5. The run was killed or interrupted | It is run again, uncounted. A killed continuation of uncommitted work is continued again. | Built. |
| 6. An input changed: the item's block, its fence, the backend policy or the tillr build | Nothing. A prose or metadata edit to an item's block does nothing to its work, and an in-flight workflow is not invalidated. The operator's `tillr drain retry`, a design answer and the recovery of a killed run still move an item. | Built. |
| 7. An authorization names a run that is no longer the item's latest | The authorization no longer speaks, and the item's latest ending routes it as if there were none. | Built. |
| 8. The machinery failed (infrastructure class) | The item holds on its own backend with the measured cause, the closed backend is an alarm, and no other backend is tried ([`D-JL24`](#415-no-automatic-move-to-another-model-d-jl24-to-d-jl27)). | Built as [recorded backend availability](../../tillr-drain/README.md#recorded-backend-availability). An infrastructure ending closes that backend, and a later run of any other class or a successful probe reopens it. An adapter preflight refusal that prints `run-<adapter>: refused: …` on exit 2 is `AttemptRefused` rather than infrastructure, holding the item as `adapter-refused` without closing a backend ([`D-JL17`](#410-bounded-run-ids-per-item-staging-holds-and-adapter-preflight-refusals-d-jl17)). A restart, a policy edit or elapsed time is not evidence that a broken harness works again. |

The rule has the shape of [`D-JL9`](#43-how-a-design-runs-ending-moves-its-conflict-d-jl9). A count is a guard built around bugs, so the bugs are fixed instead, and each ending names who moves it. The returned ending is the planner's reason `returned-with-evidence`. Holds are derived from the store on every pass. The drain README's section [A refused run goes back to its worker](../../tillr-drain/README.md#a-refused-run-goes-back-to-its-worker) states the built rule and its tests.

**When verifier refusals need triage.** Owner, 2026-11-20: “Are the refusals changing? Like, two or three refusals, okay. Ten, something's wrong. Seventy, like, the process is horribly broken and needs something changed and it will never complete. And just like randomly trying another model is not the solution here.”

**From an operator request; the owner may overturn it.** No count of verifier refusals holds an item. A `verify-not-done` refusal returns to the worker carrying every unanswered finding and the full reason, including reproduction text. A later `done` verdict answers the findings for that criterion. The item is held only when the latest refusal repeats a finding that the worker received and claimed to fix by submitting a candidate whose cited file contents (or whole judged tree when the finding is not file-scoped) did not change. The hold names that finding and gives the operator the `tillr drain retry` command. Retry starts a fresh repeat comparison without erasing the feedback. Other endings keep their own routes.

**Why a repeated landing conflict restarts from the current trunk (`D-JL12`).** Parking an item on its second identical conflict leaves the operator only one useful move: closing and refiling the item so work starts fresh from the current trunk. The owner ruled on 2026-11-19 and 2026-11-20 that the drain takes that one fresh start automatically: on the second identical `squash-conflict` within the current retry cycle, discard the candidate (releasing any replayed dirty or repair holds and settling any open landing call on that candidate), reset the lane to the current trunk, and return the item through the planner as a fresh workflow attempt from its first stage rather than an inline `-cfix` copy of the last stage's request and seat. Its brief keeps the item's source reference (`body_ref` or saved request words), omits conflict-fix `Settled decisions` and marker-reapply instructions, states that the earlier attempt conflicted twice, and names the conflicting paths. Only when that fresh attempt conflicts again at landing does the drain park the item for the operator (`WaitingOn: "owner"`, `conflict-owner`), whether or not the hunks changed and whether or not a document block or `design` seat exists; an explicit `tillr drain retry` starts a new retry cycle.

### 4.5 What a Worker May End With (`D-JL11`)

The owner ruled on 2026-11-18 that a worker must not be handed a sanctioned way to end without delivering. A brief that offers `RESULT: failed` and a list of "stop and report" conditions gets them taken: measured on 2026-11-18, one model ended 19 of 61 drain runs `RESULT: failed`, most of them after a few read-only commands, and sending the same brief again changes nothing. The owner's words: "if you don't want that path, don't expose that path. And if it is a valid path — they can't make forward progress — we need a way to take another action rather than just telling them to do the same thing again." **Rule: a worker run has two endings. The goal is the commit. The only other ending is a named obstacle: a fact the worker cannot change, of one closed set of kinds, together with what it needs. Each kind leads to a different action, and none of them sends the same worker the same brief again.**

**Whose decision is which.** The principle and the quotation above are the owner's. The five built kinds, their required fields and the route of each were chosen by the session's coordinator on the owner's delegation (he may overturn any of them); the sixth kind (`delivery`) and its automatic fork-restaging route were ruled by the owner on 2026-11-19 ([`D-JL15`](#48-planning-time-fork-delivery-the-delivery-obstacle-and-patch-branch-refusal-d-jl15)).

**`fence` is not a kind.** On 2026-11-19 the owner asked of a fence route, "didn't we already rule that this is basically impossible and wasteful?" and answered the operator's proposal to remove it, "yes, file that." The mechanism is from the operator request, which the owner may overturn: a report naming `fence` is a missing output, not a design conflict, a retry with wider paths, or an operator hold. The [common deny-list](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-vocabulary.md#51-the-work-and-its-statement) is a pre-gate check, not an obstacle. A match returns the entry and reason to the worker. It reads only the candidate's committed change; a ref or other shared state that moved while the run was open is recorded by the run boundary check and never refuses the candidate (the designer's [`D-VO14`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-vocabulary.md#D-VO14), which the owner may overturn). Which worker may add an item declaration is the designer's [`D-VO13`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-vocabulary.md#D-VO13), which the owner may overturn: a saved idea's turn and a triage may add theirs, and nobody may edit or remove one. The judge gets the diff and changed paths and checks that the change does what the words ask and nothing more.

The report names the obstacle with a line `OBSTACLE: <kind>`, then that kind's fields, each on its own line, and ends `RESULT: blocked`. A field's value runs to the next field or the footer, so evidence may span lines.

| Kind | When | Required fields | What the loop does |
| :--- | :--- | :--- | :--- |
| `definition` | The item's words are wrong or contradict the tree | `CRITERIA`, `EVIDENCE` | Raises a design-seat conflict. The design seat amends the block or objects ([`D-JL9`](#43-how-a-design-runs-ending-moves-its-conflict-d-jl9)) |
| `trunk` | The base is red, and this change did not cause it | `CHECKS` (gate check ids), `BASE` | Replays the named checks on the run's base. Every one red there: the trunk fixer is filed or attached to, and the item waits on it, released when it lands. Otherwise the run goes back to its worker with what the replay found |
| `tooling` | A tool or the harness is defective | `COMMAND`, `EVIDENCE`, `PATHS` | Files a defect item, ranked with trunk fixers, whose criterion is that the command completes and the evidence's failure no longer reproduces. The item waits on it, with the tooling as mover, and is released when it lands or someone closes it. The defect item is named by a digest of the command, so a second report of the same command, from any item, attaches to the one item |
| `seat` | An attempt the worker made and tested shows the task exceeds this model | `TRIED`, `MISSING`, and a changed worktree | A seat obstacle from a run that left the worktree unchanged from its base is a missing output, because its evidence is the attempt. Otherwise the item moves to the next backend on the backend policy's `escalate` list for its seat, for every later run until it lands. That next run is a fresh run with the obstacle in its brief, because the seat changed. Past the end of the list, a design-seat conflict asks for a plan or a split. The same model is never run again for the item after it names `seat`. Whether this route stays is [OQ-JL5](#OQ-JL5). The list is backend names; seat semantics are [the planning design's](tillr-planning-node-model-tiering.md#4-kinds-of-work) |
| `owner` | A decision only the owner can make | `QUESTION` | Raises a design-seat conflict carrying the question. The design seat answers it from the documents, or objects `NEXT-ACTOR: owner` and writes the question in its report, where the owner reads it. A worker never raises a direct owner hold |
| `delivery` (not built) | A worker discovers mid-run that its change belongs to a fork it was not staged for | `FORK` (a name on the repository's fork list) | Restages the same item as a fork piece (with a fork checkout, worker non-delivery instructions, fork gating, and lander-owned fork delivery) and continues it without blocking for the operator ([`D-JL15`](#48-planning-time-fork-delivery-the-delivery-obstacle-and-patch-branch-refusal-d-jl15)) |

**What is not an ending.** `RESULT: failed`, a `blocked` report without a complete obstacle, a kind outside the set, and a run that stops with neither commit nor obstacle are each a missing output. Without a commit, the run goes back to its own session as ending 1 of [`D-JL10`](#44-how-a-worker-runs-ending-moves-its-item-d-jl10), and the refusal says what is missing and states the two endings. In the pi adapter the same check runs inside the session before it settles, so the worker is answered in place without a new run. With a commit, the candidate is judged like any other. The identical-repeat rule is what ends that loop, never a count. The brief lists, as work to continue rather than obstacles, a patch that does not apply cleanly, a merge conflict, a failing test in the work being changed, a long suite, and work not yet done. Stored records that carry a `failed` or `trunk-broken` footer are still read: both keep their meaning in workflow nodes, and a `trunk-broken` footer with the trunk fields reads as a `trunk` obstacle.

**A generated repair item**, meaning a trunk fixer or a defect item, has no design block, so the design seat cannot amend its criterion. A `definition`, `owner` or `tooling` obstacle from such an item goes to the owner. The loop writes the question from the obstacle's own fields. A trunk fixer follows the same deny-list as every other worker; files changed since green do not determine what it may repair. A trunk fixer may not name `trunk`, since the red trunk is its work. A repair item's `tooling` obstacle files no second defect item, because a repair waiting on another repair could not pass its own gate on a red trunk. A legacy `NEXT-ACTOR: owner` line from a fixer is still read.

**A request that says when nothing is to change (designer's decision; the owner may overturn it).** When a request's words state the condition under which nothing is to change, and the worker's report shows that condition with the commands it ran and their results, the item is finished with no candidate and is closed with that evidence as the reason. Nothing is built, and no commit is owed. That finding is not a `definition` obstacle: `definition` means the item's words are wrong or contradict the tree, and here the words named the case in advance and the tree agrees with them, so the design seat has nothing to amend.

On `planned-build@v1` the request need not pre-state the condition (`D-JL34`): an investigation whose reproductions establish that the repository needs no change ends with `no_change` ([Section 4.21](#421-an-investigation-that-finds-nothing-to-change-ends-inside-tillr-d-jl34)), is checked by `verify` against the item's criteria, stores the structured finding on the item, and closes it (`closed`). Outside `planned-build@v1`, or without the required finding fields and independent judge pass, reporting "nothing to change" remains a missing output.

**Rejected:** treating the finding as a `definition` obstacle (it spends a design run on a conflict with no decision in it); an empty or token commit made to satisfy the commit goal; answering the conflict with `NEXT-ACTOR: build` (the worker has nothing to build).

**Not built.**

- The report footer is to be replaced by one tool call, the design of [the landing call](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-landing-call.md). Where an adapter has no such call, the footer above is the contract.
- An obstacle naming another item that must land first (graph-doc rule 14) is not a kind yet. The route would be a queue edge plus a resume after that item lands.
- In a multi-node workflow, a node's blocked report takes the design-seat route whatever its kind. The `trunk`, `tooling` and `seat` routes apply to single-worker runs.
- The `delivery` kind of [`D-JL15`](#48-planning-time-fork-delivery-the-delivery-obstacle-and-patch-branch-refusal-d-jl15).
- The trunk replay runs off the store's write lock and in a scratch worktree of its own. It still runs inside the settling lane's turn, because a refuted claim continues that lane's session.

The code is `tools/tillr-drain/drain/obstacle.go` and `obstacle_route.go`, the brief's **Report shape** in `tools/tillr-run/backends/brief-template.md`, and the in-session check in `tools/tillr-run/backends/pi/keep-going.ts`. Both readers are tested against one case file, `tools/tillr-run/backends/pi/testdata/obstacle-cases.json`.

### 4.6 A Held Item Never Occupies a Lane (`D-JL13`)

On 2026-11-19 the owner ruled: *"I want you to ensure that each lane is full as long as something is schedulable there at all points and make any changes to make that the case."* **Designer's rule to meet that goal (`D-JL13`); the owner may overturn it:** a held item must not reserve a lane merely because it is waiting. Whenever an item goes on hold with unlanded work in its lane, the drain saves that work under a ref it owns and records the ref on the item, resets and returns the lane to rotation in the same pass so any schedulable item can take it immediately, and restages the work from the recorded ref onto whichever lane the item next starts on. Every view (`tillr-drain why`, `tillr-view waiting`, the item page, and the Observatory) shows where the held item's work is kept rather than reporting an idle kept lane.

Four code paths can keep a lane for a held item, and `D-JL13` applies the same ref-save, same-pass release, restage, and view-display rule to each:

| Path keeping a lane | Hold reasons / cases | What `D-JL13` requires |
| :--- | :--- | :--- |
| **`retiredHeadKeep` (`recordedHeadKeep` in [`held_lane.go`](../../tillr-drain/drain/held_lane.go))** | Any candidate hold whose lane `HEAD` is the loop's document-retirement commit (`WorkerHeadSHA != ""` and `RetirementTreeSHA != ""`), which `refs/tillr/runs/<run>` does not pin. | Save the retirement commit under a drain-owned ref recorded on the item, release and reset the lane in the same pass, and restage the retired head onto whichever lane next examines or runs the item. |
| **`retainLane` returning `keep = true` ([`held_lane.go`](../../tillr-drain/drain/held_lane.go), [`workflow_evaluator.go`](../../tillr-drain/drain/workflow_evaluator.go))** | `backend-window` / `backend-closed` when a review awaits an open backend (`errJudgeBackendHeld`), and `gate-no-verdict` (`errGateNoVerdict`, when the gate answered `"error"` without reaching a verdict). `errRepairPending` is an active conflict-fix handoff. | For `gate-no-verdict`, save the candidate and unlanded lane state, release the lane and restage on the next gate pass. Backend-held judges retain the lane under `D-JL27`. |
| **`lanestate.KeepReason` worktree-coupled holds ([`lanestate/read.go`](../../tillr-drain/lanestate/read.go))** | Held multi-node workflows (`workflow == true`), held fork-delivery candidates (`baseRef != ""`), `host-boundary-violation` (`boundary == true`), `candidate-record-mismatch` / unrecorded lane `HEAD`, and holds entered before a `Candidate` is recorded (`!hasCandidate`). | Save the worktree state — including staged workflow artifacts and commits, fork-checkout commits and base refs, or unrecorded or boundary-flagged commits — under drain-owned refs recorded on the item, clear and return the lane in the same pass, and restage onto whichever lane next runs or inspects the item. |
| **Quota-paused single-worker runs (`quota_pauses` in [`quota_continue.go`](../../tillr-drain/drain/quota_continue.go))** | `backend-window` when a run is paused on backend quota (`state = 'waiting'`), leaving `work.Done == false` and `work.LaneReleased == false` on the paused lane. | Save the paused lane's committed and uncommitted work under a drain-owned ref recorded on the item, release the lane in the same pass so items on open seats or backends can run, and restage the work (with session continuity when available) onto whichever lane resumes the item when the window opens. |

**Judge waits keep their lane ([`D-JL27`](#415-no-automatic-move-to-another-model-d-jl24-to-d-jl27), designer's decision; the owner may overturn it).** A change waiting for a judge whose backend cannot run is an alarm under `D-JL25`, so it keeps its lane and its inputs until the alarm is fixed; `backend-window` and `backend-closed` on the review seat are not part of the release work.

**Safeguards (from an operator request; the owner may overturn it).** For a pinned candidate, a gate that reaches no verdict releases the lane, with these safeguards: restage on another lane, refuse a missing or mismatched pin, and recover an interrupted release. Release and restoration are tested separately for a held multi-node workflow and for a fork checkout: restoring the top-level candidate alone does not restore the workflow artifacts or the fork's work. Before a candidate exists, or when the lane head is unrecorded, release only if the work can be preserved and restored; otherwise report the specific reason the lane is kept. Never reset or release a lane under a live member run.

A failure to save to git, reset the checkout, or reap a finished run's surviving child processes (`preserve-failed`, pin/reset failure, or `lane-children-alive`) is a lane fault, not a reservation for a waiting item.

**A fifth path ([`D-JL30`](#417-a-backend-wait-holds-a-lane-only-for-work-that-is-in-it-d-jl30), designer's decision from an operator request; the owner may overturn it).** A node whose run was refused at its first message, and changed nothing, does not keep its lane as ready unfinished work until the backend window opens. It is released under the rule of [Section 4.17](#417-a-backend-wait-holds-a-lane-only-for-work-that-is-in-it-d-jl30).

### 4.7 Offered Commits, Own-Candidate Lanes, Unlaunched Claims, and Named Hold Movers (`D-JL14`)

An item must not be stranded when its next step is offered the lane holding its own unlanded change. Without these rules, staging refuses the item's next node with `lane-holds-unlanded-change` once the trunk has moved past the lane's base; cancelling that staging ends the workflow's pending work, the lane goes out of rotation, the item falls into `run-link-missing` with no named cause, and the worker's commit sits on the lane branch with no `refs/tillr/runs/` pin.

Four requirements from an operator request, adopted by the designer as `D-JL14`; the owner may overturn the decision:

1. **Pin every offered commit as soon as it is offered.** When a finished writing run offers a commit — at landing-call intake (`intakeLandingOffer` in [`tools/tillr-drain/drain/landing_call.go`](../../tillr-drain/drain/landing_call.go)), at writing-node settlement before advancing to the next node (`settleNode` in [`tools/tillr-drain/drain/workflow.go`](../../tillr-drain/drain/workflow.go)), and when a candidate is deferred for judgment (`settle` in [`tools/tillr-drain/drain/loop.go`](../../tillr-drain/drain/loop.go)) — the drain immediately pins it at `refs/tillr/runs/<run_id>` so no later step can leave it reachable from a lane branch alone. On a fork-series lane whose isolated checkout (`laneTarget(lane) != lanePath(lane)`) holds a commit absent from the repository root, the root pin is skipped rather than failing `git update-ref` on a nonexistent root object, while any commit present in the root and every ordinary lane commit is pinned.
2. **Allow an item's next node to start on or restage from its own unlanded candidate.** Holding the item's own candidate is never a reason for staging to refuse (`lane-holds-unlanded-change`). In [`tools/tillr-drain/drain/lane_copy.go`](../../tillr-drain/drain/lane_copy.go) (`clearableLaneCopy`, `prepareContinuedLane`) and [`tools/tillr-drain/drain/stage.go`](../../tillr-drain/drain/stage.go) (`Stage`, `refuseUnlandedCommit`), when a lane commit belongs to the same item (`call.offered`, `drain.candidate-ready`, `drain.node-advanced`, `drain.candidate-lane`, or a returned worker session) and no foreign active pending work owns the lane, staging ensures `refs/tillr/runs/<run_id>` pins it and restages or resets from the pin as the workflow requires, carrying the item's original `ItemBaseSHA` (`pendingItemBase` in [`tools/tillr-drain/drain/loop.go`](../../tillr-drain/drain/loop.go)) when continuing on a lane whose local `item_base_sha` file was not written by that item.
3. **Retract any claim that could not launch, offer the item again in the same pass, and return the lane to rotation.** In [`tools/tillr-drain/drain/item_fault.go`](../../tillr-drain/drain/item_fault.go) (`cancelStaging`) and [`tools/tillr-drain/drain/unlaunched_claim.go`](../../tillr-drain/drain/unlaunched_claim.go) (`retractClaim`, `restorePendingBeforeClaim`, `releaseUnlaunchedClaims`), cancelling a claim that never started retracts every store effect the claim wrote (`dispatches`, `seat_dispatches`, `read_only_runs`, `node_runs`, `node_reused`, the lane lease, and any conflict move) and, when the claim continued a `drain.node-advanced` or `drain.graph-changed` workflow step, restores that pending work rather than marking the run examined. [`tools/tillr-drain/drain/pass.go`](../../tillr-drain/drain/pass.go) and [`tools/tillr-drain/drain/plan.go`](../../tillr-drain/drain/plan.go) re-plan in the same pass — keeping any lane refused in that pass in `OutLanes` for the rest of the pass so a waiting node moves onto a free lane (`work.Ready && !work.Done && OutLanes[work.Decision.LaneID]`), and offering any item freed by the retracted claim — while [`tools/tillr-drain/drain/lane_rotation.go`](../../tillr-drain/drain/lane_rotation.go) (`recheckLanes` / `ProbeLane`) returns a `lane-holds-unlanded-change` lane to rotation as soon as its `HEAD` is retained by `refs/tillr/runs/` or `TrunkRef`, without waiting for `laneRecheckInterval` or a working-tree change.
4. **Name the hold reason and its mover; `"cause not recorded"` is neither.** The `retryHoldReason` fallthrough (`unclassifiedRunReason` in [`plan.go`](../../tillr-drain/drain/plan.go)) names what the store's records show for the item and latest run (no run record, missing run row, missing finish record with run state, or finished run state, end cause or node outcome with no recorded refusal or landing), and `For` in [`holdrules.go`](../../tillr-drain/holdrules/holdrules.go) matches `run-link-missing: <detail>` prefixes. Every entry of `holdrules.Rules` names a concrete mover. A change to a mover in the hold rules changes what the waiting CLI and API display, so the view's waiting assertion, home-page fixture and README change in the same commit.

The four requirements are built. The [claim tests](../../tillr-drain/drain/unlaunched_node_claim_test.go) cover same-pass reoffer and return of the lane; the [candidate tests](../../tillr-drain/drain/pin_and_own_lane_test.go) cover immediate pinning and starting the next node after trunk moves. The [hold-rule tests](../../tillr-drain/holdrules/holdrules_test.go) check that the detailed `run-link-missing` reason resolves to a rule with a named mover.

Requirement 4 answers *why is the item held, and who can move it?* The waiting view also reports *how did the last run end?* Keep `end cause not recorded` when that run’s termination cause is unavailable, as [`TestWaitingHeldLastRunEndCause`](../../tillr-view/waiting_end_cause_test.go) requires. It is a suffix after the mover, never a substitute for the hold reason or the next action. No waiting-view edit remains for this request.

### 4.8 Planning-Time Fork Delivery, the `delivery` Obstacle, and Patch-Branch Refusal (`D-JL15`)

On 2026-11-19 the owner ruled (`D-JL15`, paired with [`D-PT9`](tillr-planning-node-model-tiering.md#59-deciding-fork-versus-repository-delivery-at-plan-time)): *"There should not be a way to mis-file an item such that it leads to bad downstream work. That should be decided later in the process."* The case behind it is a request for a change to a fork that is filed with repository paths rather than the lane's fork checkout.

Four rules make fork handling a decision of planning and execution rather than filing:

1. **No path list at filing.** `tillr item request` ignores `--path` with a notice, and fork work is never routed from a path list. Built.
2. **Delivery classification before build.** The `plan` step of `planned-build@v1` — and, on a single-worker item, a short read-only first step with the same job — decides from the item's words and the tree whether the change delivers through repository files, one named fork from the repository's fork list (read by [`delivery.go`](../../tillr-drain/drain/delivery.go)), or both as two pieces in order (fork first, then the repository files that depend on it), and the drain stages, gates, and lands each piece accordingly. Built.
3. **Automatic restaging on `OBSTACLE: delivery`.** When a worker discovers mid-run that its change belongs to a fork it was not staged for, it ends with `OBSTACLE: delivery` and `FORK: <name>`, in both [`obstacle.go`](../../tillr-drain/drain/obstacle.go) and the shared worker ending contract in [`tools/tillr-run/backends/`](../../tillr-run/backends/) (`brief-template.md`, `pi/keep-going.ts`, `pi/obstacle.ts`, and `pi/testdata/obstacle-cases.json`); the drain restages the same item as a fork piece and continues it without blocking for the operator. Not built: `obstacle.go` has no `delivery` kind.
4. **A worker never delivers a fork itself.** The drain refuses before the gate any candidate whose run (or attempt) moved a fork's delivery branch, excluding lander-marked deliveries.

### 4.9 Keeping a Live Trunk Fixer's Work When a Rerun Passes (`D-JL16`)

A trunk check can fail, get a `fixer-main-<sha12>` item filed for it, and then pass on a later proof run while the fixer's worker is still running. If `resolveProvedFixers` ([`fixer_resolve.go`](../../tillr-drain/drain/fixer_resolve.go)) moves the fixer item to `resolved-elsewhere` at that moment, a worker that has already found and fixed the real cause — an intermittent test — is left with a fix on a lane branch that [`terminal_item.go`](../../tillr-drain/drain/terminal_item.go) refuses to gate or land because the item is terminal (`item-already-terminal`), and a resolved fixer's unfinished or resumed run record can go on showing as live.

Two requirements (`D-JL16`), both built:

1. **A check that fails and then passes with no change between is an intermittent failure, not a repair; let a live fixer finish and land any commit it produces.** When a recorded proof rerun covers an open trunk fixer's checks in `resolveProvedFixers` ([`tools/tillr-drain/drain/fixer_resolve.go`](../../tillr-drain/drain/fixer_resolve.go)) — or when `resolveStaleFixer` ([`tools/tillr-drain/drain/fixer_rebase.go`](../../tillr-drain/drain/fixer_rebase.go)) finds the fixer's checks green on the trunk tip — `drain.fixer-proved` still records the passing proof once since the latest filing or red attachment so both acquitted items waiting behind the fixer ([`repairedTrunkWaiter` in `tools/tillr-drain/drain/trunk_release.go`](../../tillr-drain/drain/trunk_release.go)) **and** ordinary queue planning (`trunkFixerOpen` / `plan.go` in [`tools/tillr-drain/drain/trunk.go`](../../tillr-drain/drain/trunk.go) and [`tools/tillr-drain/drain/plan.go`](../../tillr-drain/drain/plan.go)) are released rather than held behind a check that now passes. However, if the fixer's run is still live — including a newly claimed or running first-turn or retry dispatch that holds a leased lane, unexamined `drain.dispatch-started`, `dispatches`, `node_runs`, or `read_only_runs` before `run.Apply` writes a `runs` row, as well as a non-terminal or `run.resume`-reopened `runs` row — or if its latest run produced a committed candidate awaiting examination (`runs.event_seq` not yet covered by a newer `drain.run-examined`) or returning from its latest `drain.refusal` on that segment (gate refusal in [`events.go`](../../tillr-drain/drain/events.go), landing conflict in `recordConflict` in [`conflict.go`](../../tillr-drain/drain/conflict.go), or judge refusal in `holdJudge` in [`judge.go`](../../tillr-drain/drain/judge.go)) with `HeadSHA != ""`, `BaseSHA != ""`, and `HeadSHA != BaseSHA` (`Step != RefusalNoOp`) bound to the fixer's latest run, the drain leaves the fixer open and lets it finish:
   - **Ends with a commit:** gate and land that commit through the fixer gate and lander as the fixer's own change (`landed`), titling the landed commit once before gating as a fix for an intermittent check (`fix: intermittent check <checks>`, keeping the worker's message in the body).
   - **Ends with no commit** (including `RefusalNoOp` / `candidate-no-op` in [`loop.go`](../../tillr-drain/drain/loop.go) where `HeadSHA == BaseSHA`, an obstacle with `HeadSHA == BaseSHA`, or having no live run and no committed candidate on its latest run when the rerun passed): resolve the fixer as `resolved-elsewhere` (`commit:<proof.commit>`) rather than returning `RefusalNoOp` to the worker.
2. **End and settle every resolved fixer's run records so none shows as live.** Whenever a trunk fixer reaches `resolved-elsewhere` (or is found already `resolved-elsewhere` with leftover run or lease state), the drain ends any locally owned running process or reader and settles its store records (`runs`, `run.finish`, `read_only_runs`, `node_runs`, `quota_pauses`, pending `drain.run-examined` examination state, and `lanes` via `run.Apply` and `ReleaseLaneInTx`, alongside [`end_unfinished_runs.go`](../../tillr-drain/drain/end_unfinished_runs.go)). That settlement covers pre-`runs` leased dispatches, non-terminal `runs` rows, and any `runs` row already in a non-paused terminal state when a resumed segment (`run.resume` sequence above `runs.event_seq`) or an active examination lease still keeps the lane leased and the run projected as live (reading `backend` and `started_at` from the `runs` row). Deterministic `Loop.pass` tests (no load- or timing-sensitive sleeps) must verify a first-turn claimed fixer before `runs` is populated, ordinary queue dispatch releasing once a kept fixer's proof passes, a kept fixer ending through `RefusalNoOp` (`HeadSHA == BaseSHA`) closing as `resolved-elsewhere`, and `settleResolvedFixerRuns` settling paused, `run.resume`-reopened, and examination-leased records while still in those states, with `yolo-packs/tillr/` mirrored via `just pack-sync`.

*(Amended by [`D-JL36`](#423-a-later-green-proof-resolves-a-trunk-fixer-whose-worker-has-finished-and-whose-candidate-waits-to-gate-d-jl36), designer's decision from an operator's filed request — not ruled by the owner; the owner may overturn it: keeping a finished worker's unexamined candidate open to gate and land applies to a same-commit rerun on the red commit itself, whereas a later green proof on a descendant of the fixer's red commit resolves a fixer whose worker has finished and whose candidate waits to gate as `resolved-elsewhere`.)*

### 4.10 Bounded Run IDs, Per-Item Staging Holds, and Adapter Preflight Refusals (`D-JL17`)

A run ID that gains a word on every continuation turn grows without bound. Past the 255-byte filesystem component limit, creating its `<lane>/durable/<run_id>` directory fails with `file name too long` (`ENAMETOOLONG`), and when that error exits the drain loop it takes down the whole drain rather than holding the one item.

Three requirements (`D-JL17`), all built:

1. **Bound every run ID's length across any number of restarts and long stems.** Continuation counts belong in one numeric counter or in the record, never as repeated words in the run ID. `markRunID` in [`run_id.go`](../../tillr-drain/drain/run_id.go) writes `-<kind>` on the first continuation and `-<count>-<kind>` thereafter, and the counter advances past 999 without clamping or repeating marker words. `attemptRunID` ([`plan.go`](../../tillr-drain/drain/plan.go)) and `boundRunIDBase` bound a long stem with a deterministic digest, preserving trailing `-judge` / `-cfix` tags and idempotence, and `stagedNodeRun` ([`workflow.go`](../../tillr-drain/drain/workflow.go)) recovers archives across bounded mixed continuations. A test pins that a run continued 100 times (and past 999 mixed turns and long stems) keeps a distinct ID strictly under 120 characters.
2. **Hold one item with a named mover when staging its run fails, and keep the loop running.** Any staging failure attributable to one item's run (creating or writing its run or durable path, an error naming the run or item, a per-run step on its lane, or `stageParallel` on its readers) retracts that run's unlaunched claim (`cancelStaging`), frees the lane, counts zero `InfraFailures`, and records a durable item fault `stage-failed` (`ReasonStageFailed` in [`item_fault.go`](../../tillr-drain/drain/item_fault.go) and [`definition.go`](../../tillr-drain/drain/definition.go)) with a named operator mover in [`holdrules.go`](../../tillr-drain/holdrules/holdrules.go) (`fix the staging fault the detail names, then tillr drain clear-fault --item <item>`). The loop keeps running so sibling items dispatch in the same pass, while shared failures that belong to no single run (such as an unrenderable brief template) keep loop-level fault handling.
3. **An adapter's refusal of a brief is the item's fault, not the backend's, and it is stopped at its cause, never by an attempt limit.** In [`preflight.sh`](../../tillr-run/backends/preflight.sh) (`preflight_brief`), a backend adapter exits `2` with `run-<adapter>: refused: …` when a staged brief cannot be run. `AdapterRefusal` / `ClassifyAttempt` ([`failover.go`](../../tillr-drain/drain/failover.go)) classify any such exit as `AttemptRefused`, holding the item at once as `adapter-refused` (`holdAdapterRefusal` in [`item_fault.go`](../../tillr-drain/drain/item_fault.go)) with the adapter's words and the operator as mover, and closing no backend. Classifying it as infrastructure would close the backend for a fault that belongs to one item's brief. [`stage.go`](../../tillr-drain/drain/stage.go) stages literal `{{` pairs carried in an item or workflow field intact, alongside a `brace-literals` count that `preflight.sh` reads, so such text is not mistaken for an unfilled template placeholder.

### 4.11 Instant Start Decisions From a Background-Maintained Queue View (`D-JL18`)

Asked on 2026-11-19 whether re-ranking the queue may stop cancelling starts already planned, the owner ruled (`D-JL18`):

> *"yes, no need to cancel scheduling, but also a few seconds is still too long. this should be an instant decision. It's totally okay if our decision of what to start is like a few seconds old, 30 seconds old, or whatever. This is never going to be the thing that makes the difference. 30 seconds is pushing it, but if you need to know what open questions there are, to know if it's blocked on a document or whatever, you can... run some background scanner with inotify... to decide what to start up, you look at the list, you look at the number of slots open, and if there's one open, you start it. There shouldn't be massive decisions going on here."*

A pass that rebuilds the full plan synchronously from the store and tracked documents, and re-checks each planned start against `items.rank`, `items.updated_at` and `TrunkRef`, takes seconds and drops remaining starts whenever queue order or `main` moves. `D-JL18` replaces per-pass start planning with three rules:

1. **Maintain an in-memory view of what can start, synchronized off the start lock.** The loop keeps an in-memory start view (`tools/tillr-drain/drain/start_view.go`, `start_watcher_linux.go`, `start_watcher_other.go`) holding the ordered queue, each item's derived holds, and free lanes. Rather than rebuilding per pass, the view updates from the loop's own writes, store changes made by other processes, document and question changes observed by a filesystem watcher (`inotify`) on tracked documents and the saved question index, and Git ref updates — including both `TrunkRef` and the proved commit ref `refs/tillr/green` so ordinary lanes cut from the proved commit when `lane_base == "green"` and from `TrunkRef` when `lane_base == "tip"`. Background synchronization (`syncStore`) reads the store, Git, and documents on a private copy outside the view's mutex (`sv.mu`) and installs it under `sv.mu` while replaying claims, releases, and holds recorded during the read, refreshing run history (`readRunHistory`), prior runs (`readPriorRuns`), freed/rotation lanes (`laneOutOfRotation` agreeing with `rotationLanes`), and queue entries incrementally only when their inputs or backend availability changed (never omitting a closed backend from latest outcomes so it looks open, and tracking the next future backend window and lease expiry rather than re-querying all past rows on every `run.*` event). Cached view facts may be up to 30 seconds old; every invariant that must be exact — the item is not already running, no hold was recorded before the claim, the backend is open, and the lane is free — is verified in the single short SQLite write transaction that claims the lane, keeping external Git and filesystem I/O outside the write lock.
2. **Decide and claim starts immediately on lane release or item filing, and record `claim_ms`.** Whenever a lane frees or an item is filed, the loop decides the start from the in-memory view at once (`runFastStart`): the first eligible item in queue order takes the free lane without waiting for the next planning pass. There is no fixed millisecond acceptance threshold. Releasing a lane (`markLaneFree` across [`tools/tillr-drain/drain/pass.go`](../../tillr-drain/drain/pass.go), [`tools/tillr-drain/drain/held_lane.go`](../../tillr-drain/drain/held_lane.go), [`tools/tillr-drain/drain/loop.go`](../../tillr-drain/drain/loop.go), and [`tools/tillr-drain/drain/lane_rotation.go`](../../tillr-drain/drain/lane_rotation.go)) frees a lane recorded at claim (`noteStartClaimed`) immediately and wakes `runFastStart` without waiting for `syncStore` to fold the store delta, including callers that pass an empty lane ID when lanes return to rotation or leases are reaped (`recheckLanes`, `reapedAny`). Launching a fast-started run while sibling lanes are staging or cleaning bumps the `laneChanges` epoch so [`boundary.go`](../../tillr-drain/drain/boundary.go) (`closeAsyncBracket`) never convicts clean runs of scope escape. Add a start-claim latency counter (`claim_ms` / `ClaimMS`, recording milliseconds from a free lane and ready item to the claim write) to `drain_passes` ([`tools/tillr-drain/drain/timing.go`](../../tillr-drain/drain/timing.go), [`tools/tillr-drain/drain/pass_observation.go`](../../tillr-drain/drain/pass_observation.go)) and surface it in `tillr view passes` ([`tools/tillr-view/passes.go`](../../tillr-view/passes.go), [`tools/tillr-view/README.md`](../../tillr-view/README.md), and Observatory pass types and styles).
3. **Never cancel a decided start on re-rank or trunk advance; keep non-start pass work off the start path; and measure in an isolated copy.** Queue re-ranking or `TrunkRef` advancing never cancels a start already decided — it affects only subsequent start decisions — and `rank` plus rank-only `updated_at` bumps are removed from the start's `inputVersion` check. Everything else a pass performs (settling, judging, proof, and housekeeping) remains, without delaying starts and without writing one hold transaction per held item. Deterministic, non-load- and non-timing-sensitive tests in `tools/tillr-drain/drain/` and `tools/tillr-view/` verify that re-ranking between decision and claim does not cancel the start, a hold recorded before the claim does, an item filed while the loop is busy settling starts without waiting for settlement, immediate lane release (named and empty lane IDs) wakes fast start without waiting on `syncStore`, `syncStore` performs store/Git/document reads outside `sv.mu` and rebuilds only changed inputs, every event fold selects the kinds it reads (`TestEveryFoldReadsTheKindsItSelects`), and the watcher updates the view on a tracked document change. Measuring filing-to-start latency on the live store before and after (excluding worktree staging) must use a throwaway Git repository (`git init` in the run's own scratch directory) over a copied store — never constructing a `Loop`, proof, or lander whose `Root` is `/workspace` or any checkout sharing `/workspace/.git` (`refs/tillr/green` and `.git/tillr-gate`), and never setting or inheriting `TILLR_LOOP_STORE=/workspace/.tillr/state.db` in a test.

#### What to split and how to judge it

On 2026-11-20 the owner revised the latency target:

> this is my fault for using a hyperbolic target. A few milliseconds to me was a wild guess. Obviously, improvement is improvement, so land the improvement. We can put a lower priority change to make it better ... if you want to land it in smaller pieces, sure, do that right now.

and added: “Split it up. That's always a good way to go.” Measured that day, filing to start took **406–752 ms** with the start view, down from **2.4–3.6 s** without it. That improvement is accepted; no fixed millisecond target applies.

**Designer’s decision on the operator request; the owner may overturn it.** Work of this size lands as independently landable slices, each naming its files, behavior, proof and the reason it can land without its successor, with a budget below 600 source lines outside tests. The remaining claim write-lock hold (`run.finish` records read from the beginning) is lower priority and not a condition for the rest.

### 4.12 Verify exits without a verdict; gate refusals without detail (`D-JL20`)

A missing `eval.output` is a consequence, never a cause. A verify run whose adapter refuses its brief never reaches the verifier, and recording the resulting file-open error as `judge-unreadable` would send the item back to planning.

**Designer's decision from the operator request; the owner may overturn it.** When a verify run exits without `eval.output`, record the verify run ID, its exit code and that it wrote no verdict. Keep the candidate and completed nodes: the next workflow node is verify, not plan. Who can act first depends on why the file is absent:

- If the adapter explicitly refused the brief on exit 2, include its refusal words and apply `D-JL17` before interpreting the missing file. Hold the item as `adapter-refused` for the operator; do not close a backend. Once the operator fixes the brief and clears the hold, resume at verify.
- If the verifier ran but exited without writing its verdict, return the candidate to verify directly. Do not call an absent verdict an unreadable one or treat it as a finding against the candidate. A file that exists but cannot be read or parsed is a different failure.

Every gate refusal has nonempty detail: it names the failing check from the verdict when there is one; if the gate produced no verdict, it says so and gives the gate log location. The structured check evidence (the failed check ids and their reproduction commands) is kept in either case.

### 4.13 What the attempt number and refusal counts tell the operator (`D-JL21`)

An attempt number that jumps while an item waits hides the distinction between an item waiting and an item repeatedly refused at verify.

**Designer’s decision from the operator request; the owner may overturn it.** The first dispatch of an item is attempt 1. Each actual redispatch after a refusal, conflict or hold advances that item's number by exactly one. Recording a hold or revisiting it over many planner passes does not advance it. Ordinary progression to the next workflow node stays in the same attempt. Show a restarted interrupted run as a restart of the same attempt, not as another try.

`tillr drain why` and the item page show how many times **this item** was refused, separately for verify, gate, fence and conflict. Count the refusal when it occurs, not each time a pass observes its consequences. For example, if attempt 1 conflicts at landing, the conflict tally becomes 1; when its producer is dispatched to repair it, the operator sees attempt 2 and one conflict. That repair continues the producing node. It is not the fresh workflow from the first stage that `D-JL12` requires after a second identical conflict.

These lifetime tallies and the attempt number describe history. No tally triggers escalation, including for the [verifier repeat hold](#44-how-a-worker-runs-ending-moves-its-item-d-jl10). Routing still follows the ending and its evidence under `D-JL10` and `D-JL12`.

**What counts as an attempt.** The planner takes the next number from the highest attempt among an item's node records (the `node_runs` table, one row per workflow node per attempt). Claiming a node writes that row before any run exists, and a claim that never starts is retracted or marked superseded with the row left behind. Counted naively, each pass over a held item could claim, retract and raise the number without a worker starting.

**Designer's decisions from the operator's filed request; the owner may overturn them.**

- **An attempt is counted from run evidence only.** A node record raises an item's attempt number only when a run recorded for that item stands behind it. A claim, a retracted claim and a superseded claim are not evidence that an attempt ran.
- **Abandoned claims are cleared at the next claim.** When a workflow item is claimed again, its superseded node records that no run stands behind are removed first, so none can occupy the node and attempt being offered or stand above a real outcome. Events and every record backed by a run are kept.
- **A hold reports the attempt that ran.** `tillr drain why` plans a hold with the number the next dispatch would take. When no dispatch is planned and no continuation holds that number, it shows the previous number, which is the attempt that actually ran.
- **A restart is drawn inside its attempt.** The item page groups a single-worker item's runs by the attempt recorded when each was dispatched, or by the attempt in the run ID when that record is missing. A restarted run joins the attempt it restarts. Runs carrying neither take the lowest unused numbers, in order.
- **The delivered copy is not a separate piece.** The copy of `tools/tillr*` under `yolo-packs/tillr/` is regenerated by `just pack-sync` in the commit that changes the source, as `D-PT8` in [the planner's Section 5.4](tillr-planning-node-model-tiering.md#54-when-the-planner-cannot-plan) requires. A piece asked only to regenerate it finds nothing to change once the writing pieces have done so. That outcome is the piece finished, not a contradiction in the request, and the candidate goes on to verify.

**Rejected:** excluding skipped node records from the count (it does not address a claim that never ran); a cap or reset of the number; treating the regeneration piece's empty diff as a `definition` obstacle.

### 4.14 When a workflow restart is claimed but never starts (`D-JL22`)

A claim is not a running successor. A restart decision can carry `workflow_restart: true` and a `node_start_run_id` naming an ended run while the successor it claims never starts; what tells the two apart is whether `tillr run status` finds the successor's run with a start.

**Designer’s decision from the operator request; the owner may overturn it.** Restart the interrupted node on the same backend; for a backend failure, hold the node as `backend-closed` until its own backend reopens (`D-JL24`). When a claim did not launch, use the `D-JL14` recovery: release its lane and offer the pending node again without an operator retry. If the node cannot proceed, report the hold and what will move it, and leave its lane available to other items (`D-JL13`). Do not wait on the ended predecessor or reserve capacity for a successor that never started.

Before changing claim recovery, reproduce a reservation that survives it: check both the item's next dispatch or named hold and whether another ready item can use the released lane.

### 4.15 No Automatic Move to Another Model (`D-JL24` to `D-JL27`)

**The owner's words.** Two statements of 2026-11-20 are the only owner rulings in this section. Everything else in it is the designer's, written from an operator request, and the owner may overturn any of it.

- About 10:55 PM ET, on a failed run being handed to a different model: "why does Terra having some error mean that we automatically flip to Sol? I don't like that. I hate fallbacks. Fallbacks are almost always wrong. We need deliberate choices, not fallbacks. We need to fix what's wrong. We don't need to just randomly try something else."
- About 11:05 PM ET, on a judge whose model is closed or out of quota: "What does it mean for a judge's model to be unavailable? We have never had that. If it's unavailable, you raise a giant alarm and we fix it."

**What was measured.** At 9:41 PM ET on 2026-11-20 a run's resume ended with pi's error "Agent is already processing", and two seconds later the same node was dispatched to a different model. The error was a defect in resuming one session. Nothing about it said the first model could not do the work, and nothing about it was fixed by the second.

**What is not automatic failover.** Escalation: a worker's `seat` obstacle moves the item to the next backend on the policy's `escalate` list ([Section 4.5](#45-what-a-worker-may-end-with-d-jl11)). It is triggered by a worker's tested attempt, not by a failure of the machinery, and whether it stays is [OQ-JL5](#OQ-JL5).

#### A failed run holds with its cause (`D-JL24`)

**Designer's decision from the owner's words above; the owner may overturn the mechanism.** The drain never moves a run, a node or an item to a different backend because something failed. There is no failover and no preference walk. What a seat runs on is one backend the policy names, and changing it is an edit to the policy by a person.

1. **An infrastructure ending holds the item on its own backend.** The ending is classified and recorded, and it closes the backend ([recorded backend availability](../../tillr-drain/README.md#recorded-backend-availability)). The item waits as `backend-closed`. Its hold states what was measured: the run, the backend, the exit code or end cause, and the last error words the harness wrote. No other backend is tried, for a single run, a workflow node, a parallel reader or a judge.
2. **The mover is the operator.** The closed backend is an alarm (`D-JL25`). The operator fixes what the cause names and records the evidence with `tillr-drain probe-backend`. A later run on that backend that ends outside the infrastructure class also reopens it. A restart, a policy edit or elapsed time reopens nothing.
3. **When the backend reopens, the same node runs again on the same backend,** in its own session where the adapter can resume it. That is a re-run on evidence that the backend works, which [the cooldown-removal design](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/failure-diagnosed-not-waited-out.md) requires before anything runs again.
4. **An identical infrastructure ending of the same item does not run a third time.** When the re-run of step 3 ends with the same backend, end cause and normalized error words as the item's previous infrastructure ending, the fault belongs to that item's run and not to the backend: another item's success would otherwise reopen the backend and send the item round again. The item is held for the operator with both runs' records, whatever the backend's state. This is the identical-repeat rule of ending 2 applied to the machinery, with the operator in place of the design seat because the design seat cannot repair a harness.
5. **Same-backend paths are a separate question.** A killed or interrupted run restarts on its backend (ending 5); a resumed session that is gone is replaced by a fresh session on the same backend; a session pi ended for a repeating call gets one fresh session on the same backend and then holds. This decision removes every move to another backend and nothing else; it is not a ruling that these three paths are kept. [The fallback inventory](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-fallback-inventory.md#3-the-inventory) rules on each:

   | Same-backend path | The inventory's ruling |
   | :--- | :--- |
   | A resume that failed is replaced by a fresh session on the same backend | Row `S1`: remove, and hold `resume-failed` (designer's). Class 4 of [the inventory's build order](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-fallback-inventory.md#4-what-the-remove-rulings-ask-for-in-order). |
   | A run whose process vanished across a loop restart runs again from the start | Row `S13`: remove, and hold `run-lost` (designer's). Class 1 of that order. A run that was killed or interrupted and whose restart is not that case still restarts on its backend. |
   | A session pi ended for a repeating call gets one fresh session on the same backend | Row `B7`: keep, awaiting the owner under [OQ-FB1](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-fallback-inventory.md#OQ-FB1). |

   **Rejected:** folding the `S1` and `S13` holds into this decision, because each needs its own loud failure and test and the inventory orders them separately; waiting for [OQ-FB1](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-fallback-inventory.md#OQ-FB1) before removing the walk, because the answer changes only the fresh session.
6. **The policy.** A seat names one backend. There is no `preference` key. A seat that lists several backends without shares is refused when the policy is checked, with a message that says to name one, because an ordered list has no meaning except a walk. Seat shares and picks ([the drain README](../../tillr-drain/README.md#seat-backend-shares-and-selection)) are a written choice of which backend a new item starts on; a share is drawn first, and an item whose drawn backend is closed waits for it.
7. **Stored records stay readable.** The reasons `failover`, `seat-degraded` and `workflow-node-failover`, and run IDs carrying the `failover` marker, are not written and keep their display rules.

**Rejected:** keeping the walk for seats that list several backends; keeping it behind a policy switch; trying the same backend again without evidence that it reopened; a count of failures before holding.

#### A backend or a judge that cannot run is an alarm (`D-JL25`)

**The owner's words fix two things: it is an alarm, and it is fixed. The rest is the designer's decision; the owner may overturn it.** A missing grant is not an alarm: no grant exists ([Section 6](#6-the-judge-is-a-step-in-the-flow)).

An **alarm** *(the word is the owner's; this definition is coined here)* is a statement that part of tillr itself cannot run, shown ahead of every item on every operator face until the fact that raised it is gone. A wait is about one item and what it needs. An alarm is about the machinery, and it lists the items behind it.

| Alarm | Raised by | Cleared by | The operator's move |
| :--- | :--- | :--- | :--- |
| **Backend closed** | The backend's latest recorded ending is in the infrastructure class | A successful `tillr-drain probe-backend`, or a later run on it ending outside that class | Fix what the cause names, then probe |
| **Backend out of quota** | Its quota window is shut, or its quota reading is stale or failing | The reset time the provider stated, or a fresh reading under the reserve | Wait for the reset shown, or change the policy deliberately |
| **Judge cannot run** | The review seat's backend is under one of the two alarms above | That backend's alarm clears | The backend's move |

1. **It is derived, not stored.** An alarm is read on every pass from facts the store already holds (`backend_outcomes`, `backend_windows`). Nobody raises or clears one by hand, and its "since" is the time of the fact.
2. **Where it shows.** First, before any count or item row, in `tillr view status`, `tillr drain why`, `tillr view waiting` and the Observatory's header bar. Each alarm prints what cannot run, since when in Eastern time, the measured cause, how many items and how many lanes are behind it, what clears it, and the command for the operator's move. The loop prints one line when an alarm starts and one when it ends, and names every active alarm in each pass summary.
3. **A face that a script can test.** `tillr view alarms` prints the active alarms and exits 1 when there is any, so a keeper or a scheduled check-in can act on it without parsing text.
4. **Never a quiet wait.** The hold rules have a class `alarm`, sorted first, with the operator as mover. `backend-closed` and `backend-window` are in it. A test fails when any backend-unavailable reason is in another class.
5. **The loop keeps running.** An alarm stops no pass. Seats on other backends keep dispatching, and nothing is sent anywhere else to get around the alarm.

**Rejected:** leaving a quota window a quiet wait because it has a reset time (the owner's words on the judge name out-of-quota); stopping the loop on an alarm; a stored alarm that someone must clear.

#### Quota exhaustion is not an exception (`D-JL26`)

**Designer's decision, read from two earlier owner rulings; the owner may overturn it.** In the drain, a run refused for quota waits for its own backend's window, and no other backend continues it.

- **The run.** A paused run stays in `quota_pauses` and resumes on its own backend when the window reopens. A first-message refusal that did no work waits as `backend-window` and is dispatched on the same backend at the reset. A new dispatch that would pass the reserve waits. The closed window is an alarm (`D-JL25`) that names its reset time.
- **Who chooses the alternative.** The owner or the operator, by changing the policy. The owner's ruling of 2026-11-20 on [`OQ-LD2`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-live-drain-config.md#OQ-LD2) says so: "I will manually switch them right now and restart." A switch a person makes is a deliberate choice, and what a switch does to a paused run is [the seat-profiles design's](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-seat-profiles.md) to say.
- **An automatic alternative has one allowed shape, and none exists.** The owner's ruling of 2026-10-20 allows a quota fallback only where the seat set explicitly enables it, announced, and "never a generic out-of-quota reaction". That ruling is about the pi session layer. This row does not amend it, and no drain policy enables anything under it. Multi-backend setups are in [the roadmap's Icebox](../tillr/roadmap.md#icebox) by that ruling, and that design is where an owner-enabled alternative would be specified.
- **Left to the owner, with nothing waiting on it:** whether the words of 2026-11-20 withdraw that earlier ruling as well. The designer reads them as leaving it standing, since an alternative the owner defined and enabled is a deliberate choice. [`OQ-DSP2`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-seat-profiles.md#OQ-DSP2), which asks whether the Claude subscription profile pauses or spills over, is still his to answer; this row matches its option A and does not answer it.

**Rejected:** continuing a quota-refused run on the next open backend of its seat; walking to another backend when a reading reaches the reserve.

#### The lane release for judge waits is dropped (`D-JL27`)

**Designer's decision; the owner may overturn it.** [`D-JL13`](#46-a-held-item-never-occupies-a-lane-d-jl13) releases the lane of a held item. A finished change that waits for its judge (`backend-window` or `backend-closed` on the review seat) is the exception: under `D-JL25` that wait is an alarm a person fixes, so the lane is kept.

- A change waiting for a judge under an alarm keeps its lane and its inputs (`retainLane` returns `keep` for `errJudgeBackendHeld`). Releasing the lane risks losing inputs the judge needs, and that risk is not taken for a state meant to last minutes.
- The alarm prints the lanes it holds, so the cost is in the same line as the fault. The owner's ruling of 2026-11-19 that every lane is full while anything is schedulable is met by fixing the alarm, not by making it cheaper to leave standing.
- Every other hold of `D-JL13` is unchanged: held multi-node workflows, fork checkouts, pre-candidate holds, unrecorded heads and quota-paused single-worker runs are released with their work saved.

#### Open: does a worker's `seat` obstacle still move the item to a stronger model ([OQ-JL5](#OQ-JL5))

The owner's words are about a model that errors. Escalation is something else: a worker that made and tested an attempt reports that the task exceeds its model, and the item moves to the next backend on a list a person wrote in the policy. Whether that is a fallback or a deliberate choice is not something his words settle, and [`OQ-DSP1`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-seat-profiles.md#OQ-DSP1) has an option that depends on it. So it is asked as [OQ-JL5](#OQ-JL5) and nothing about escalation is built or removed until he answers. `D-JL24` does not depend on the answer.


### 4.16 An operator retry that waits for a lane says so (`D-JL29`)

A retry the operator authorizes with `tillr drain retry` and that no lane can take stays planned across passes. If its reason code names the ending that preceded the retry, and the hold rules (the table in `tools/tillr-drain/holdrules/holdrules.go` that gives each reason its class and its mover, the party or event that advances the item) give that code the mover "the next pass", the reader is told of a refusal that did not happen and a next pass that changes nothing.

**Designer's decisions from the operator's filed request; the owner may overturn them.** The reason name, the sentences and the holder wording below are the designer's, not the owner's.

- **An authorized retry carries its own reason.** A retry the operator authorized is recorded as `operator-retry` (`ReasonRetry` in `tools/tillr-drain/drain/schema.go`). `harness-refused` stays in the hold rules for stored records only, so a decision recorded under it still resolves to the class and mover it was written with.
- **A retry the plan can start names its lane.** `tillr drain why` and the Waiting page say "operator retry planned for `<lane>` (lane is free)", and the mover is "dispatch the authorized retry on `<lane>`".
- **A retry the plan cannot start says it is waiting for a lane, and names what holds each one.** The text is "operator retry waiting for a lane", followed by every offered lane the retry could take and its holder: unfinished work for a named item with its run, an active lease with its run, an item that took the lane earlier in the same plan, or a lane reserved for a named item. The same holders are listed as what the item waits on. When no eligible lane is offered at all, the text says so and the mover is to offer one with `--lanes`.
- **Eligibility is the planner's own.** An express retry can take an express or an ordinary lane; an ordinary retry can take only an ordinary lane; a desk is never listed. A retry that must return to the lane keeping its candidate lists only that lane.
- **The human table changes; the machine code for a lane wait does not.** The plain `tillr drain why` table prints the sentence above in its reason column. The JSON form keeps `no-lane` as the reason of a retry waiting for a lane, so a reader of that field is not broken.
- **The delivered copy is not a separate piece**, as [Section 4.13](#413-what-the-attempt-number-and-refusal-counts-tell-the-operator-d-jl21) decides.

**Rejected:** keeping `harness-refused` as the live reason and changing only its mover text (the name itself reads as a refusal); "the next pass" as the mover of a retry that waits on a lane; reporting "no lane" without naming the lanes and their holders; renaming the JSON `no-lane` reason; removing the `harness-refused` rule, which would leave recorded decisions without a class or mover; a trailing regeneration-only piece (`D-JL14`, `D-JL21`).

### 4.17 A backend wait holds a lane only for work that is in it (`D-JL30`)

**What was measured.** On 2026-11-21 one backend was refused for quota for about three hours ("hit your 5-hour limit"). For that whole time almost no lane had a worker, while `tillr drain why` listed 12 to 14 items as waiting only for a lane (`no-lane`), among them single-worker items whose only backend was open.

**The rule, from the operator's request; the owner may overturn it.** "No fallback to another backend, no timer: the fact to check is whether the item has anything in a lane."

**The cause that was confirmed.** A node whose first run ends at its first message with a quota refusal has changed nothing. If the loop records the node as ready to start again, and `pendingDecisionExcept` in `pass.go` answers `backend-window` for a ready node whose backend is shut, that unfinished work is not marked lane-released, so `readLanes` and `tillr drain why` count the lane as busy until the window opens. An item that has never run holds no lane: the `case windowShut` arm of `planner.decide` in `tools/tillr-drain/drain/plan.go` answers a `backend-window` hold before any lane is assigned, and the claim in `pass.go` declines with "the dispatch backend window closed" before any lease is written. The delivery step that `planDelivery` puts in front of a single-worker item (`classify`, in `tools/tillr-drain/drain/delivery.go`) runs on the `plan` seat, so an item whose work runs on an open backend can still wait on a closed one for its first step.

**Designer's decisions from the operator's filed request; the owner may overturn them.** The mechanism and the test shape are the designer's, not the owner's.

- **One fact decides.** An item that waits for a closed backend (`backend-window` or `backend-closed`) holds a lane only when it has something in that lane: an unlanded commit, an uncommitted change, a workflow's staged output, a fork checkout's work, or a live run. A lane holding none of these is free in the same pass. No lease, no reservation, no unfinished-work record and no assignment made earlier in the same plan may keep it.
- **An item that has never run holds nothing.** The plan holds it before any lane is offered, and the claim declines before any lease is written. A test pins it so the order cannot be reversed unnoticed.
- **A first-message refusal that changed nothing holds nothing.** When a node's run ends in a quota or backend refusal and the lane's head and worktree are what staging left, the loop releases the lane in the pass that records the refusal. The item waits as `backend-window` with no lane, and at the reset its node is planned onto any free lane (the `work.LaneReleased` branch of `planItems`). This is the fifth path of [Section 4.6](#46-a-held-item-never-occupies-a-lane-d-jl13).
- **A refused run that left work is the fourth row of Section 4.6**, unchanged: the work is saved under a drain-owned ref, the lane is released, and the work is restaged when the window opens.
- **A finished change waiting for its judge keeps its lane** under [`D-JL27`](#415-no-automatic-move-to-another-model-d-jl24-to-d-jl27). It has something in the lane, so this rule and that one agree.
- **No other backend and no timer.** The item starts on its own backend when the window opens (`D-JL24`, `D-JL26`). Nothing releases or reclaims a lane because time passed; the release happens in the pass that records the refusal, and the only later event is the window opening.
- **The report tells the two waits apart.** An item whose first step's backend is closed is reported as `backend-window` or `backend-closed` with that backend named, and never as `no-lane`. `no-lane` is reported only when every lane the item could take has a named holder, the listing `D-JL29` already requires for a retry.

**Tests.** One test builds the measured state: four offered lanes, two of them express; a refused first node recorded as ready on one ordinary lane; the other ordinary lane released after a fixer that is blocked on its owner; three unstarted items whose first step is on the shut backend, two of them express; and ordinary and express items that run on the open backend. It asserts what the plan and `tillr drain why` answer for each item. Another asserts that an item whose first message was refused restarts on another lane at the reset, and that a refusal which left a commit or a change is not released by this path.

**Rejected:** releasing a lane after a waiting time; starting the waiting item's first step on another backend; keeping the lane of a refused first message so the item restarts in place (it has nothing there to restart from).

### 4.18 A fork piece's brief states the write scope that staging enforces (`D-JL31`)

A fork piece is a node staged on the lane's fork checkout rather than on the repository worktree. Staging narrows a copy of the node's write scope to the paths inside the fork checkout (`forkFence` in [`delivery.go`](../../tillr-drain/drain/delivery.go), applied in [`stage.go`](../../tillr-drain/drain/stage.go) and [`resume.go`](../../tillr-drain/drain/resume.go)). A scope that names only repository paths narrows to nothing, which staging reads as "inherit the fork fence", so the enforced fence is the whole fork checkout.

If the node line of the brief ("This node may write only these paths") is written from the node's scope as recorded, before that narrowing, the brief's **Fence** section and its node line name two lists with no path in common, and a worker that reads both has no path it may write.

**The decision (`D-JL31`), the designer's, from an operator's filed request; the owner may overturn it.**

1. **On a fork piece, the fork checkout fence is the node's write scope.** The paths under the brief's **Fence** heading are what the run may change. A repository path in the node's recorded scope grants nothing on a fork piece and forbids nothing in the fork checkout.
2. **The brief states one scope, the one staging enforces.** The node line is written from the same narrowed value that staging writes to the run's fence (`workflowNodeBrief` in [`node_brief.go`](../../tillr-drain/drain/node_brief.go)). When narrowing leaves no path, the brief prints no node line, because the node then inherits the fence above it. A brief never lists a path that does not exist in its target. A repair node's brief is written by the same function and follows the same rule. Built.
3. **A brief that contradicts itself is a defect in the tool that writes it, not a contradiction in the request.** A stop reported as a wrong definition goes to the design seat, and the design seat can only edit documents; nothing in a design document reaches a build worker's brief. A stop reported as a defective tool makes the drain file a repair for the tool and hold the item until it lands, which is the route such a defect needs. Measured on 2026-11-21: one model, given the same contradictory brief eight times, stopped six times and worked twice, and neither a design answer nor an operator's retry reason carried in the brief outweighed the line "This node may write only these paths".
4. **A planned delivery names exactly one fork** (`deliveryPrompt` in [`delivery.go`](../../tillr-drain/drain/delivery.go)), so a change that spans two forks is two requests, delivered in order.

**Tests.** One stages a fork piece whose node scope names only repository paths and asserts that the brief has no "may write only" line and that its Fence section names the fork checkout. A second stages a fork piece whose scope names a path inside the fork checkout and asserts that the node line lists that path, rewritten to the lane's checkout, and no repository path. A third stages the repair node of a fork piece and asserts the same as the first.

**Rejected, by the designer.**

- *Widening the item's fence to add the fork checkout.* The fence of a fork piece is already the fork checkout; the item's repository paths are for a repository piece.
- *Having the planner rewrite the node's scope to fork paths.* The planner cannot know the lane, and [`D-JL15`](#48-planning-time-fork-delivery-the-delivery-obstacle-and-patch-branch-refusal-d-jl15) makes the drain, not the plan, turn a delivery decision into a staged checkout.
- *Telling the worker the correct reading through a retry reason.* A sentence in the brief does not outweigh a line of the same brief that says "This node may write only these paths".
- *Building on another seat or model so that it reads past the node line.* The brief is wrong, not the worker: a worker that stops on two lists with no path in common is doing what its brief says.
- *Recording a hold in this document.* Nothing in the drain reads a design document before it starts a node.

### 4.19 A worker returned by a design answer starts from a trunk that holds the answer (`D-JL32`)

Two different things are called a conflict, and they must not be read as one:

- A **landing conflict** is a candidate commit that does not apply to the trunk when the lander squashes it on (the landing result `squash-conflict`).
- A **design conflict** is the record the drain writes when a worker ends `RESULT: blocked`. It holds the worker's report and names who answers it. The decision reason `conflict-design` in the loop log is the dispatch of the design seat to answer one. It says nothing about a landing.

A landing conflict never dispatches the design seat: it goes back to the worker that produced the candidate (row 1a of the table in [Section 4.4](#44-how-a-worker-runs-ending-moves-its-item-d-jl10), made by `conflictFix` in [`conflict.go`](../../tillr-drain/drain/conflict.go), which dispatches with the reason `conflict-fix` on the candidate's own seat). The design seat runs for a filed request, which has no item block in a document, when its build worker ends on a definition obstacle: the design seat is asked to update the decision ledger of the design document under `docs/` (`requestObstacleDesignInstruction` in [`obstacle.go`](../../tillr-drain/drain/obstacle.go), reached from [`blocked.go`](../../tillr-drain/drain/blocked.go)), and a design commit that passes the gate and lands is the answer (ending 4 of [Section 4.3](#43-how-a-design-runs-ending-moves-its-conflict-d-jl9)).

**The failure this section closes.** After a design answer, the worker's base is moved forward to the commit the answer landed at (`blockBaseAt` and `designAnswerLanded` in [`lane_base.go`](../../tillr-drain/drain/lane_base.go)). When the design run's candidate conflicts at landing, the `landings` row under the design run's id says `squash-conflict` and the `landed` row is under the conflict-fix run's id. A lookup by the design run's id alone then finds nothing, the worker is staged on its old base, reports the same obstacle about that old tree, and each report buys one more design run and one more record. Measured on 2026-11-21: 12 of 31 trunk commits in two hours were design records, several of them repeats produced this way.

**The decision (`D-JL32`), the designer's, from the operator's filed request; the owner may overturn it.**

1. **The routing of a landing conflict is not changed.** A landing conflict returns to the worker that produced the candidate, on the latest trunk, whatever seat that worker holds. No test for "replays cleanly" or "conflicts only in files the candidate changed" chooses a seat, because no seat is chosen there: the design seat is never dispatched on a landing result. `TestSecondIdenticalConflictDiscardsCandidateResetsLaneAndRestartsWorkflowFromFirstStage` and `TestFreshAttemptConflictParksForOwnerRegardlessOfBlockDesignSeatOrHunks` in [`conflict_restart_test.go`](../../tillr-drain/drain/conflict_restart_test.go) exercise that path.
2. **A worker returned by a landed design answer is staged on a commit that contains the answer, whichever run landed it.** A design answer that lands through one or more conflict-fix runs is the same answer as one that lands directly. The commit to contain is the trunk commit the answer's landing produced. `designAnswerLanded` finds it by the head of the candidate that answered the conflict, recorded on the conflict when the answer is recorded.
3. **The test.** In a fixture, a filed request's build worker ends on a definition obstacle; the design run's commit conflicts at landing; its conflict-fix run lands while the proved-trunk pointer still names the older commit. The test asserts that the next build run's base is the landed commit and that its lane's tree holds the answer's file. A second case lands the answer after two conflict-fix runs in a row.
4. **The lookup does not read a run id suffix.** It must not depend on reading the `-cfix` suffix out of a run id, because [tillr-graph-is-the-path.md](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-graph-is-the-path.md) deletes that suffix (its criterion c4: "The conflict-fix run and its run-id suffix are deleted").
5. **No count is added.** Nothing here counts attempts, conflicts or design runs, as `D-JL9` and `D-JL10` rule.

**Two causes this decision does not close.** Each is its own request:

- **The returned worker's brief does not name the design answer.** A worker staged on a base that holds the answer can still report the obstacle the answer settles, because the request's words are unchanged and nothing in its brief points at the record.
- **A repeated obstacle is recognized only when its evidence is word-for-word the same.** `repeatedAnsweredObstacle` in [`answered_obstacle.go`](../../tillr-drain/drain/answered_obstacle.go) holds an item for the operator when a worker reports, after a design answer, the same obstacle on the same criteria with the same `EVIDENCE` text. Reports that name the same criteria and the same fact in different words are not held. The exact comparison was chosen so that a second, different gap in one criterion is not mistaken for the first; what replaces it is undecided.

**Rejected** (the designer's rejections; the owner may overturn them):

- *Routing a landing conflict by whether the candidate replays cleanly or by which files conflict.* It adds a branch to a path that already sends every landing conflict to the producer.
- *Sending a filed request's definition obstacle back to its build worker in place of the design seat.* A first obstacle about the request's words is a real one and the design seat answers it correctly. The waste is the repeats, not the first answer.
- *Stopping after a number of design answers.* No count applies, and the repeats end when the worker sees the trunk.
- *Keeping each request's design record out of a shared file to avoid landing conflicts.* Where a record belongs is decided by its subject, and a conflict in a shared document costs one conflict-fix run and delays no code.

### 4.20 Leftover Work in a Lane Is an Alert, Never an Automatic Sweeper (`D-JL33`)

**Owner ruling, 2026-11-21.** Earlier the same evening, of a lane that was found out of rotation with leftover work, the owner said: "I'm a little worried that if you put a fixer for this without knowing why it got there, we will just be covering over some issue." Later on 2026-11-21, the owner ruled: "It seems to me that this sweeper should actually be part of tiller watch because this should just be an alert that there's work left over. You can like then manually clean it and file the root cause, but there should not just be like work left over at a random time."

Only those two quoted statements are the owner's words. How they map onto `tillr`'s utilities, events, and workflows below is **from the operator's filed request and the designer's decision (`D-JL33`); the owner may overturn those mechanics**.

1. **No part of `tillr` clears, resets, or sweeps a lane's leftover work automatically.** Neither `tillr-drain` (in staging, settlement, or `recheckLanes` in [`tools/tillr-drain/drain/lane_rotation.go`](../../tillr-drain/drain/lane_rotation.go)), nor `tillr-watch`, nor any background pass or helper utility clears, resets, or sweeps leftover uncommitted or unretained work found in a lane. Saving a live item's work under a drain-owned ref recorded on that item when placing that item on hold ([Section 4.6](#46-a-held-item-never-occupies-a-lane-d-jl13), `D-JL13`) or advancing its own workflow ([Section 4.7](#47-offered-commits-own-candidate-lanes-unlaunched-claims-and-named-hold-movers-d-jl14), `D-JL14`) settles an active item's known transition; leftover work sitting in a lane from an ended run is an unexplained fault and is left untouched until a person or operating agent inspects it.
2. **Leftover work in a lane raises a `tillr-watch` alert for manual clean-up and a root-cause item.** Leftover work in a lane is a fault to be found:
   - `tillr-watch` raises an alert when leftover work is present in a lane or keeps a lane out of rotation (`drain.lane-refused`), executing no automatic remedy ([OQ-TW2](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-watch.md#OQ-TW2) in [`tillr-watch.md`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-watch.md#63-mode-a-mechanical-answers-inside-tillr-and-non-wasting-drain-triage-d-tw7-oq-tw2-oq-tw4)).
   - Answering the alert, the operating agent saves the leftover work, cleans the lane by hand so `recheckLanes` (`drain.lane-restored`) can return it to rotation, and files a `tillr` item for the root cause that left the work behind.
3. **Fixing a cause that leaves work behind is still wanted and is distinct from sweeping after the fact.** An automatic clearer or sweeper acts *after* leftover work already sits in a lane for an unknown reason, hiding the defect that put it there. Fixing a cause that leaves work behind in the first place — for example, closing an item (`tillr item close`) whose run left uncommitted work in a lane without settling that worktree — prevents the leftover from arising rather than covering over an unknown leftover after the fact, and remains wanted as root-cause repair work.

**What is built and what is owed:**

- **Refused in `tillr-drain`:** Staging refuses a lane and takes it out of rotation (`drain.lane-refused` in [`lane_rotation.go`](../../tillr-drain/drain/lane_rotation.go)) with `lane-holds-uncommitted-work` when staging a retry candidate (`spec.RetryCandidate != nil` in [`stage.go`](../../tillr-drain/drain/stage.go)), when `refuseUnlandedCommit` inspects an unlanded head, or when preparing a continued, held, or preserved lane ([`loop.go`](../../tillr-drain/drain/loop.go), [`held_lane.go`](../../tillr-drain/drain/held_lane.go), [`held_fork.go`](../../tillr-drain/drain/held_fork.go), [`preserved.go`](../../tillr-drain/drain/preserved.go)), and with `lane-holds-unlanded-change` for an unretained commit; `recheckLanes` restores the lane (`drain.lane-restored`) only after the condition clears.
- **Alerted by `tillr-watch`:** the rule `drain-lane-refused` in `config/tillr/watch/` reads `drain.lane-refused` and `drain.lane-restored`.
- **Owed:**
  - Closing the automatic-wipe gaps in `tillr-drain` where `refuseUnlandedCommit` and `clearWorktree` in [`stage.go`](../../tillr-drain/drain/stage.go) remove uncommitted or untracked files when `spec.RetryCandidate == nil` and `HEAD` is already contained in `spec.BaseSHA` or `TrunkRef`, and where `discardTerminalLane` in [`preserve_hold.go`](../../tillr-drain/drain/preserve_hold.go) calls `resetLane` when `preserveWork` meets an already-terminal item.
  - Root-cause fixes for transitions that leave uncommitted work behind in the first place, such as closing an item whose run left uncommitted work.

**Rejected:**

- *An automatic lane sweeper or clearer in `tillr-drain`, `tillr-watch`, or a background check that saves, resets, or deletes leftover work found in an idle or out-of-rotation lane* (owner's ruling: covers over why leftover work appeared at a random time instead of surfacing the root cause).
- *Treating root-cause repairs that stop a lifecycle transition from stranding work in a lane (for example, when closing an item whose run left uncommitted work) as forbidden sweepers* (designer's decision from the operator's request; the owner may overturn it).

### 4.21 An Investigation That Finds Nothing to Change Ends Inside Tillr (`D-JL34`)

A worker asked to investigate a failure can establish with reproductions that the repository needs no change, whether or not the request's words pre-stated that outcome. Given only a commit or an obstacle as endings, such a worker has to raise `OBSTACLE: owner` asking whether to close the request, the item is held, `tillr-watch` alerts (`drain-obstacle-hold` in [`tools/tillr-watch/obstacle_hold_rule_test.go`](https://github.com/mschulkind-oss/tillr/blob/main/tools/tillr-watch/obstacle_hold_rule_test.go)), and the operator closes it by hand.

**Not the owner's ruling; the designer's decision (`D-JL34`), from an operator request, which the owner may overturn.**

1. **Workflow definition and ending word (smallest change).**
   - **Workflow definition: `planned-build@v1`** ([`config/tillr/workflows/planned-build@v1.json`](https://github.com/mschulkind-oss/tillr/blob/main/config/tillr/workflows/planned-build@v1.json)), already the default workflow for `tillr item request` (`RequestDefaultWorkflow["build"]` in [`tools/tillr-item/item/request.go`](../../tillr-item/item/request.go)) and the `build` seat (`workflows.default.build`). No separate `investigate@v1` workflow or filing flag is added: a filer asking about a failure does not know before reproductions run whether the trunk needs a fix commit or needs nothing, and `planned-build@v1` already carries the independent read-only `verify` evaluator (`exit.evaluator_slot: "verify"`, `judge_classes: ["verification-only"]`). `exit.requires_candidate` stays `"commit_required"` for commit endings (`land` and `RESULT: done` still require `HEAD != base`), so a worker that merely forgets to commit is still refused.
   - **Ending word: `no_change`** — one spelling across both ending capabilities: the `no_change` tool under `call-suspends` (`no_change` on Pi, `mcp__tillr__no_change` on Claude Code; [Section 3.7 of the landing-call design](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-landing-call.md#37-a-no-change-finding-is-a-third-tool-on-the-planned-build-workflow), `D-LC13`) and `RESULT: no_change` under `footer`. It is staged and accepted only on `planned-build@v1`'s `plan` stage (`id: "plan"`, `seat: "plan"`, `access: "read_only"`, `footer` capability) and unsplit whole-item `work` stage (`id: "work"`, `seat: "build"`, `access: "write"`, `call-suspends` or `footer` capability; split `build-pieces@v1` pieces keep their unchanged-piece `RESULT: done` rule). Other workflows do not expose `no_change`, keeping the owner's 2026-11-18 rule ([Section 4.5](#45-what-a-worker-may-end-with-d-jl11), `D-JL11`) that an ending is offered only where tillr takes a defined action on it.

2. **Structured finding and immediate worker checks.**
   Every `no_change` ending carries three required non-empty trimmed string fields — `cause` (what produced the observed failure or behavior), `evidence` (the reproductions run: commands, commits or inputs checked, and observed outputs), and `why_no_change` (why the repository needs no change) — whether or not the request's own words pre-stated a nothing-to-change condition:
   - **Under `call-suspends`** (on `planned-build@v1`'s unsplit `work` stage: `tools/tillr-run/backends/pi/no_change.ts` loaded alongside `land.ts` and `obstacle.ts`, and `mcp__tillr__no_change` in `tools/tillr-run/backends/claude/landing`), `no_change({cause, evidence, why_no_change})` checks immediately inside the call (`D-LC2`, `D-LC13`) and returns an in-session error without ending the turn if any of `cause`, `evidence`, or `why_no_change` is missing or blank, `HEAD != base` (a commit exists — call `land` instead), the worktree has uncommitted or untracked paths (`git status --porcelain=v1 --untracked-files=all`), the same `(base, cause, evidence, why_no_change)` was already refused in `landing-state.json`, another ending call is open, or Pi still owes a background-task wake. On a pass it writes `landing-offer.json` in the run's durable directory (`{"call_id", "tool": "no_change", "base", "finding": {"cause", "evidence", "why_no_change"}, "transcript"}`) and parks/defers (`call.offered` with `tool: "no_change"`).
   - **Under `footer`** (on `planned-build@v1`'s `plan` stage and on unsplit `work` when the adapter capability is `footer`), the report writes `CAUSE:`, `EVIDENCE:`, and `WHY_NO_CHANGE:` lines (each running to the next uppercase field header or the footer, parsed by the same multi-line field reader as `obstacle.go` and `keep-going.ts`) followed by `RESULT: no_change`. Missing fields return to the same session as a missing output; `HEAD != base`, dirty or untracked paths, or (on `plan`) a `do-it-now` or `proposal` output alongside `RESULT: no_change` refuse the node in `settleNode` (`tools/tillr-drain/drain/workflow.go`).

3. **Routing through `verify` (`c7`: independent judge check against the item's criteria).**
   A worker's `no_change` finding never self-closes an item:
   - When `plan` settles `no_change`, `plan` is recorded `'passed'`, `work` is recorded `'skipped'`, the structured finding is persisted on the attempt (`no-change.json` in the run's durable directory and the workflow attempt state), and `nextWorkflowNode` (`tools/tillr-drain/drain/workflow_order.go`) advances directly to `verify` (`evaluator_slot: "verify"`, rather than propagating `work`'s skip across the `work -> verify` edge). When unsplit `work` settles `no_change`, `work` is recorded `'passed'` with the finding and advances to `verify`.
   - `evaluatorCandidate` (`tools/tillr-drain/drain/workflow_evaluator.go`) stages `verify` at `evaluated_head = base_sha` and `evaluated_tree = base_sha^{tree}` with `JudgedActor` naming the `plan` or `work` run that produced the finding (`checkIndependence` in `tools/tillr-item/item/judge.go` enforces distinct run and session). `stageJudge` (`tools/tillr-drain/drain/judge.go`) quotes the worker's `cause`, `evidence`, and `why_no_change` in the verifier brief and instructs `verify` to reproduce and check the claim independently at `evaluated_head` against the item's words and every criterion; `checkJudgeScope` (`tools/tillr-drain/drain/judge.go`) treats `no-change.json` alongside `report.md`, `node-report.md`, and `landing-offer.json` as worker claims that `verify` may not cite as its own evidence.
   - Against a filed request's criteria (`requestCriteria` in `tools/tillr-item/item/request.go`), an independently reproduced finding that the repository already behaves as asked or that the reported failure lies outside the trunk satisfies `c1`–`c3` with no repository diff, while `c4` catches any case where leaving the trunk unchanged is an unruled policy choice reserved to the owner (which `verify` marks `blocked` waiting on `owner`, or `not-done` if the trunk in fact needs a change).

4. **Closing the item without a commit or alert (`c5`) and showing the finding on `tillr item show` (`c6`).**
   - **When `verify` passes (`outcome: "pass"`, all criteria `done`):** Neither `tillr-gate` nor `tillr-land` runs (`trunk` does not move). In one store write transaction (`tools/tillr-drain/drain/workflow_exit_record.go` / `tools/tillr-item/item/`), the drain calls `item.RecordJudge` (`evaluated_head = base_sha`, `landed` empty), stores the structured finding on the item (`items.finding` in `tools/tillr-item/item/schema.go`, carried on `itemPayload` in `apply.go` and emitted as `"finding": {"cause", "evidence", "why_no_change", "evaluated_head", "worker_run", "judge_run"}` inside `item.record` by `tillr item show` in `tools/tillr-item/item/show.go`, cleared on `item.Reopen`), transitions the item to `state: "closed"` via `item.Close` (`close_reason = "no_change: " + finding.WhyNoChange`, `closed_by = judgeRunActor`), and closes any open `no_change` landing call (`call.closed` with `reason: "closed-no-change"`, never waking the parked session). Because no `obstacles.HeldKind` event is emitted and `closed_by` names the judge run rather than `operator`, `tillr-watch`'s `drain-obstacle-hold` rule does not fire, no hand-action defect is raised ([rule `T5` / §5.3](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/operator-decisions-inside-tillr.md#53-an-item-whose-fix-already-landed)), and neither the owner nor the operator is asked.
   - **When `verify` refuses (`outcome: "fail"`):** On `not-done` (`RefusalVerifyNotDone`), the item stays `in-queue` with zero verdicts written: if unsplit `work` made the `no_change` offer, the verifier's findings return to `work` (as a `refused`, stage `judge` tool result on the open `no_change` call under `call-suspends`, recording the refused finding in `landing-state.json`, or via `verify_return.go` under `footer`; or back to `plan` if a reason begins `plan-wrong:`); if `plan` made the `no_change` claim (`work` skipped), the next attempt starts at `plan` with the verifier's findings in its brief so `plan` can plan or `do-it-now` the required change. On `blocked` or `defective`, `settleJudgeFailure` applies unchanged (`blocked` sets `waiting_on`; `defective` records `defective` verdicts and closes `"defective: ..."`).

**Rejected (designer's decision; the owner may overturn):**
- *Adding a new `investigate@v1` workflow definition* (requires choosing the outcome class at filing time and leaves ordinary `tillr item request` items on `planned-build@v1` unable to end when reproductions show nothing to change).
- *Switching `planned-build@v1`'s `requires_candidate` from `"commit_required"` to `"commit_optional"`* (`completeGraphWithoutCommit` in `workflow_exit_record.go` marks `"commit_optional"` items `landed` with mechanical `"no commit by design"` verdicts and would accept an ordinary `RESULT: done` run that forgot to commit).
- *Closing on the worker's `no_change` claim without running `verify`, or letting `verify` cite the worker's finding without running its own checks* (self-certification, violating `c7` and [rule `T5`](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/operator-decisions-inside-tillr.md#4-the-rules)).
- *Representing `no_change` as an `obstacle` kind or naming the worker ending `close`* (an obstacle means the worker is stopped from finishing rather than finished, and the drain after `verify` — not the worker — closes the item).
- *Requiring that the request's own words pre-state a nothing-to-change condition* (leaves an investigation request with no valid ending inside tillr).

### 4.22 Post-Verdict Gate-Failure Replay Never Reports `run-live` or Runs Whole-Tree Go Tests (`D-JL35`)

When a candidate's gate fails, the drain replays the failing checks on the candidate's base to tell a failure the candidate caused from a check that is already red on the trunk (`settleGateFailure` -> `settleTrunkAlreadyRed` -> `judgeTrunkChecks` in [`trunk.go`](../../tillr-drain/drain/trunk.go), calling `ProcessSteps.Replay` in [`steps.go`](../../tillr-drain/drain/steps.go)). The candidate's lane is released before the replay starts (`releaseLaneBeforeReplay`), so the replay runs in a scratch checkout under `.replay/<rev>` while another item takes the lane.

Two things go wrong when that replay is slow or unlabeled. Measured on 2026-11-23: a replay that ran every Go package of every `tools/tillr-*` module on the base took over 80 minutes, during which the two candidates had a final `gate.verdict`, no `drain.refusal`, no process matching their run IDs in `ps`, and `tillr drain why` reporting one as `run-live` and the other as `run-awaits-recovery`.

**Not the owner's ruling; the designer's decision (`D-JL35`), from an operator's filed request, which the owner may overturn.**

1. **Keep the lane release before post-verdict replay, and scope the Go replay so it completes in seconds.**
   - A custom replay program stays unchanged.
   - For the affected-Go-tests check, the default replay reads the candidate gate's `go-affected: failing packages and tests:` summary from the candidate run's gate log. When every listed failing Go package names concrete tests (no package failure with no named test and no build failure), it runs only those named tests (`go test -count=1 -run ^(?:TestA|TestB)$ <pkg>`) in `.replay/<rev>`, and records the check red on `rev` iff any named test fails there.
   - Otherwise (a compile or package failure with no named test, or no summary block), it runs the affected-package selection scoped to the candidate's changed paths (`CandidateChangedPaths`, or `git diff --name-only <base> <head>` when empty), and replays the whole check only when the candidate has no changed paths.
   - Every child process the replay spawns carries `TILLR_RUN_ID` and `TILLR_ITEM_ID` (never `TILLR_LANE_ID`, because the candidate's lane is released) and sets `gc.auto=0` and `maintenance.auto=0`, so `ps` identifies the candidate run and a test fixture does not spawn background `git gc`.

2. **Post-verdict candidate replay has its own `gate-replay` hold reason, and `tillr drain why` never reports `run-live` or a false worker recovery for it.**
   - `ReasonGateReplay = "gate-replay"` in [`schema.go`](../../tillr-drain/drain/schema.go) is registered in [`definition.go`](../../tillr-drain/drain/definition.go) and [`holdrules.go`](../../tillr-drain/holdrules/holdrules.go) (class "waits on the loop", where "gate", mover "the loop's post-verdict trunk replay for the candidate to finish and record its refusal or inherited pass"), and `Loop.pass`'s wait guard ([`pass.go`](../../tillr-drain/drain/pass.go)) includes it so the loop waits on an in-flight replay rather than declaring the queue drained.
   - `pendingDecisionExcept` ([`pass.go`](../../tillr-drain/drain/pass.go)) answers `ReasonGateReplay` for `work.Candidate != nil && work.LaneReleased && (work.Examining || work.Examiner != nil)`.
   - In [`why.go`](../../tillr-drain/drain/why.go), `work.Examiner != nil` is treated like `work.Examining` in `observeWorkers`, so an examination owned by a live `drain_sessions` loop is never downgraded to `run-awaits-recovery` when the finished worker ran under an earlier session; if the owning examiner's session has ended or its PID is dead before the claim is reaped, the report is candidate examination recovery, not `run-live` or worker recovery. `ReasonGateReplay` is presented as `moving` at position `candidate`. A run with a terminal `runs` record (and no open `run.resume` after it) or a final `gate.verdict` and no live worker process never reports `run-live`.
   - In `reapDeadLoopRuns` ([`orphan.go`](../../tillr-drain/drain/orphan.go)), reaping a dead `work.Examiner` also records the examination's release whenever `work.Examining` is true, so a workflow candidate with a released lane cannot remain stuck on `work.Examining` after an unclean examiner exit.

3. **The refusal is recorded and the item returns to a worker on completion, without a timer.** No timer re-examines released candidates. Once `settleGateFailure` establishes that the failure is not an inherited red check on trunk (green on base, or repaired at tip), `verify` records `drain.refusal` (`RefusalGate`), the examination is recorded and its ownership cleared without touching the released lane, `markExamined` wakes the start view even though no lane was released at that moment, and the pass woken by examination completion dispatches the `RefusalGate` retry back to a worker on an available lane.

4. **Tests.** `TestGateFailedReplayReleasesLaneToWaitingWork` in `tools/tillr-drain/drain/gate_replay_lane_release_test.go` (ordinary, workflow, and a worker that ran under an ended loop session) and targeted tests pin that during post-verdict replay with the lane released both the planner and `Why` report `gate-replay`; that when replay finishes with the failing check green on base, `drain.refusal` (`step: "gate"`) and `drain.run-examined` are recorded and one pass with a free lane dispatches the item back to a worker while leaving the sibling item on the released lane untouched; and that the Go replay runs only the named failing tests (or the changed-path selection), exports the run and item IDs without the lane ID, and distinguishes base-green from base-red checks.

**Rejected** (designer's decision; the owner may overturn):
- *Adding a timer or periodic re-examination pass for released candidates* (it would re-run or race an active replay).
- *Keeping candidates' lanes leased across post-verdict trunk replay* (wastes scarce worker lanes whenever replay runs).
- *Scoping the replay only inside the replayed checkout's own gate program* (leaves every replay of a base commit older than that change running the whole tree).
- *Keeping `run-live` for post-verdict replay and only adding `work.Examiner != nil` to `observeWorkers`* (a finished run with a final verdict and no worker process would report as a live worker, masking a stuck replay).

### 4.23 A Later Green Proof Resolves a Trunk Fixer Whose Worker Has Finished and Whose Candidate Waits to Gate (`D-JL36`)

A trunk fixer can finish its worker and sit in the queue as a candidate waiting for a lane to gate while `refs/tillr/green` already stands at a descendant of the fixer's red commit whose proof lists the fixer's check as passed. A queued fixer in that proof state with no worker is marked `resolved-elsewhere`; a finished candidate must be too, or it takes a lane to gate a fix for a trunk already proved green.

**How `D-JL16` and this rule fit together.** `D-JL16`'s premise is that a check that fails and then passes with no change between is an intermittent failure, not a repair, so a live fixer finishes and lands any commit it produces. When a proof commit strictly descends from the fixer's red observation (`proof.Commit != red && proof.Commit != latestRed`), commits *have* landed between the red observation and the green proof; once the fixer's worker has finished and its candidate sits waiting to gate, gating and landing that candidate spends a lane on a trunk already proved green by a later commit. Queue and fixer scheduling is engineering detail under [`OQ-PR4`](https://github.com/mschulkind-oss/tillr/blob/main/docs/tillr/decision-provenance-review.md#OQ-PR4).

**Not the owner's ruling; the designer's decision (`D-JL36`), from an operator's filed request, which the owner may overturn.**

1. **Distinguish a later green proof from a same-commit rerun in `resolveProvedFixers` (`tools/tillr-drain/drain/fixer_resolve.go`).**
   - Resolve `latestRed` for each open trunk fixer from its latest `FixerAttachedKind` event carrying a non-empty `red_sha` (falling back to `red` resolved from `TrunkFixerSHA(id)` when none is present). A covering proof (`proof.Passed(checks, seen)` for every check in `provableChecks(fixerChecks(text))`) is a **later green proof** (`laterProof == true`) when `proofPastRed` holds against both `red` and `latestRed` and `proof.Commit != red && proof.Commit != latestRed`. When `ReadCheckProofs` returns both a same-commit proof and a later descendant proof that pass `checks` after `seen`, prefer the later descendant proof rather than stopping at the first match.
   - When `laterProof == true`, `resolveProvedFixers` marks the fixer `resolved-elsewhere` (`item.SetStateWithReceipt` with `ResolvesVia: "commit:" + proof.Commit`, `Reason: proof.Describe(checks)`, `By: Utility`, recording `drain.fixer-proved` once when `!alreadyProved`) not only when the fixer is queued with no candidate, **but also when its worker has finished and its candidate waits to gate** — including when an earlier pass recorded `drain.fixer-proved` while the worker was still running and a subsequent pass (or `examineWorkerEnd` in [`tools/tillr-drain/drain/worker_gate.go`](../../tillr-drain/drain/worker_gate.go) right after the worker boundary closes, before `planWorkerSettlement`) observes the finished worker/candidate.
   - A fixer's worker **has finished and its candidate waits to gate** when no worker or examination is live (`read_only_runs` has no `settled = 0` row, `node_runs` has no `outcome = 'running'` row, no `lanes` row has `state = 'leased'` for any run of that fixer, no post-verdict examination ownership `work.Examining` / `work.Examiner != nil` is active, and no pre-`runs` `drain.started` or `dispatches` claim lacks a `runs` row), its latest `runs` row is in a non-paused terminal state (`isTerminalRunState(state)` — `exited`, `failed-to-start`, or `timed-out`) with no `run.resume` event above `runs.event_seq`, and `drain.examined` (`examinationDoneKind`) has not yet been recorded on that run (covering a settled `drain.candidate` / `drain.prepared-candidate` with `work.LaneReleased == true` waiting for a lane or gate budget, a settled candidate sitting on an idle lane with `work.LaneReleased == false` before `ActionJudge`, and a just-exited worker run before `ActionSettle` gates it).

2. **Settle the resolved candidate without gating, landing, or leaving unlanded work on an idle lane.**
   - Never gate or land a fixer candidate once the fixer is `resolved-elsewhere`.
   - When the candidate's lane was **already released** (`work.LaneReleased == true`, `drain.candidate-lane` with `released: true` and `HeadSHA` already pinned at `refs/tillr/runs/<run_id>`), settle the run in the same pass without waiting for, leasing, or restaging onto `d.LaneID`: preserve `HeadSHA` under `refs/tillr/preserved/<run_id>` (when non-empty and `!l.nonLanding`), append `drain.examined` (`examinationDoneKind`) and `drain.item-already-terminal` (`itemTerminalSettledKind`), and let `reconcileLandingCalls` close any open `call.offered` as `"superseded"`, leaving any sibling item currently leasing `d.LaneID` untouched. Also align `fixer.HasUnfinishedResolvedFixerRuns` (`tools/tillr-drain/fixer/fixer.go` and `fixer_settle.go`) with `drain`'s `"drain.started"` and `"drain.examined"` event kinds.
   - When the candidate's lane was **not yet released** (`work.LaneReleased == false`, so `d.LaneID`'s worktree still holds `HeadSHA` or uncommitted edits), `settleResolvedFixerRuns` must **not** append `drain.examined` before the worktree is preserved and reset; instead `terminalSettlementExcept` -> `settleTerminalItem` (`ReasonItemAlreadyTerminal` in [`tools/tillr-drain/drain/terminal_item.go`](../../tillr-drain/drain/terminal_item.go)) saves/pins the work under `refs/tillr/preserved/<run_id>`, resets `d.LaneID` cleanly to `main` (avoiding `lane-holds-unlanded-change` under [`D-JL33`](#420-leftover-work-in-a-lane-is-an-alert-never-an-automatic-sweeper-d-jl33)), and records `drain.examined` and `drain.item-already-terminal`.

3. **Everything else is unchanged.**
   - **Fixers still running a worker** (pre-`runs` leased claims or `dispatches`, `read_only_runs` with `settled = 0`, `node_runs` with `outcome = 'running'`, non-terminal `runs` rows including `paused`, `run.resume` above `runs.event_seq`, or an active `lanes` lease `state = 'leased'` including an in-flight `-judge` gate lease) stay open.
   - **Fixers for a check the proof does not list** (or where the proof does not descend from the fixer's red commit or predates `seen`) stay open.
   - **Same-commit reruns (`laterProof == false`, `proof.Commit == red || proof.Commit == latestRed`)** and **post-examination `drain.refusal` returns** (`examinationDoneKind` already recorded) keep `D-JL16`'s behavior.

4. **Tests.**

- *Changing same-commit rerun or live-worker behavior with this rule.*
- *Appending `drain.examined` in `settleResolvedFixerRuns` on an un-released candidate (`work.LaneReleased == false`) before its lane worktree is preserved and reset* (leaves `HeadSHA` checked out on the idle lane and triggers `lane-holds-unlanded-change`).

## 5. Core Boundary for External AutoQA (`D-JL7`)

AutoQA is a client of tillr, not a part of it. The item store has no vocabulary of its own for it: the `autoqa` actor kind, the `qa-verification` claim class and the `autoqa` decider are refused on new writes with the rule `actor-retired`, and rows that already carry them stay readable. The standalone `gate change`, `run request` and `run exec` contracts (`D-AQA2` to `D-AQA4`) stay.

1. **Authority kind and client identity are two fields.** A verdict's `actor_kind` (`mechanical`, `agent` or `human`) names the rule the store checks. Its `actor` names who ran. A client's name in `actor`, such as `autoqa/<suite>`, marks its verdicts on every read surface without a fourth kind, and the item page shows both fields.
2. **An external client crosses into tillr through four existing faces only.** [The AutoQA design](tillr-autoqa.md) is the first such client; it keeps its own queue, coverage state and false-positive memory outside the item store.
   - **File a bug or remedy item:** `tillr item apply`.
   - **Record a deterministic test result:** `tillr item verdict record` with `actor_kind: "mechanical"`, `claim_class: "verification-only"` and evidence.
   - **Record an agent's review:** a review tied to the selected workflow's judging step, with `actor_kind: "agent"`, the judged actor and evidence ([Section 6](#6-the-judge-is-a-step-in-the-flow)).
   - **Escalate to a person:** `tillr item mail send`, or a move to `blocked` waiting on the owner. Never a fifth verdict value and never a decision row decided by the client.

### Rulebook and its enforcement

The flow is a versioned definition in `config/tillr/workflows/`; `planned-build@v1` names `verify` in `exit.evaluator_slot`. The rulebook consists of the selected definition and expanded graph, the judging step's instructions and input references, and each stored `item_criteria.claim_class`. A selected expanded graph is persisted in `workflow_selections`; editing the source does not silently rewrite a selected graph. A version name alone does not make a file immutable.

**Designer's choice, owner may overturn:** an evaluator stage carries a required, nonempty `judge_classes` list. It names only `verification-only`, `red-gate-triage`, and/or `direction`; duplicates, unknown values and `owner-only` are rejected. The shipped evaluator and the compatibility judge below list only `verification-only`: the absence of a grant must not silently authorize more. A class is added by a deliberate, reviewed change to that workflow definition and, if its meaning or actor boundary changes, to the class table in `tools/tillr-item/item/`. Neither a per-run request, backend policy, model output, nor a clock widens the list. `red-gate-triage` or `direction` may be listed only when the relevant decision is not stored as `owner-only`; an owner-only decision stays the owner's even if its prose resembles either class. This describes how a reviewed widening is expressed, not an authorization to widen it now.

The evaluator must remain read-only, required, and after all writers. Its node prompt and declared inputs, candidate diff, stored criterion IDs, text, classes and hashes, producer identities, and saved request words are staged. Bind the receipt to the selected expanded graph, evaluator node, item and exact candidate head/tree; intake reads the persisted selection and checks that this is its evaluator, the class appears in `judge_classes`, and the verdict's class matches the stored class. A model-supplied label or a caller-provided class list alone is not a binding. Both dry-run and write intake enforce the same rule, including direct `item verdict record` and `item judge` agent writes; no alternate API may bypass it. New verdict events retain actor, judged actor, class, hash, reason, evidence, candidate and workflow/node provenance, but no `grant_id`. Store enforcement is a contract on recorded state and is not a claim of authentication against arbitrary database writers.

Keep `claim-class-actor` for any agent `owner-only` verdict, mechanical limited to `verification-only`, class and hash matching, evidence, completeness, independence, and the gate/landing boundaries. An absent or incompatible judging step is a definition/intake fault naming the workflow and class, not an owner renewal request. No verdict is invented if the evaluator does not answer. A passed evaluator receipt survives gate, landing and post-land recovery without rejudging or checking a clock; preserve exact-candidate checks and once-only publication. This respects [landing principles](landing-principles.md), especially refusal as a verdict and gating once; it adds no retry on trunk movement.

**No-slot routes:** an explicit evaluator invokes the judge, while a no-slot graph invokes a separate review only if `judge_mode=agent`; no-slot alone does not imply a judge. Mechanical completion stays for no-judge verification-only workflows. As a compatibility design, materialize that existing opt-in as a fixed, read-only review evaluator in the selected expanded graph, with the same prompt/inputs and `judge_classes: ["verification-only"]`; persist it before dispatch rather than issuing an implicit authority at verdict time. Do this deterministically for unselected legacy `judge_mode=agent` items and for already-selected no-slot graphs that have not yet passed judging. Already-selected graphs with an evaluator but no list gain the same verification-only list during migration. Do not insert a second judge where the graph already names one, or make every workflow judged. For an in-flight checked receipt, retain its judged bytes and candidate and adopt its existing evaluator or compatibility step without rerunning it; an absent or inconsistent binding is a named definition fault, not a fresh verdict. Graph replacement must preserve the outer evaluator and its class list. Standalone or external agent reviews need a selected workflow with such a step; an arbitrary direct agent verdict without one is refused. Human and mechanical direct verdicts keep their existing paths.

### Stores that hold grant rows

**Designer's choice, owner may overturn:** a store that holds an `item_grants` table is migrated atomically under the store's schema writer, not from read-only views. Before the table is dropped, every row's five fields are archived as inert data in an append-only migration event, ordered by ID, including rows with no matching issue event; that event is registered for reading, `item.grant` events stay decodable, and existing `item.grant` and `item.verdict` events are retained byte-for-byte, including a stored `grant_id`, actor and evidence. The archive is not an issuable grant, lookup table, authorization source or expiry. Criteria are not reclassified, deleted, rejudged or unfrozen on account of archived grants; stored verdict state remains as recorded. New stores never create `item_grants`, and new writes never issue grants or cite them. Archive, drop, graph and receipt compatibility and the migration marker commit together or roll back together; repeat opens are inert and a read-only open changes nothing. A stored receipt's `GrantID` is ignored on recovery, not copied into a new verdict. Stored `judge-grant-absent` refusal events do not project as active holds: eligible items are replanned and saved work resumes, preserving independent holds and any candidate or lane recovery. Binaries and pack copies are upgraded before a migrated store is opened: a writer that expects the removed table is unsupported, and a backup precedes migration.

**Finished-state evidence is built.** Block 5 requires completed criteria and a current receipt for `landed`, and a pointer for `resolved-elsewhere`; the reverted-landing return remains the only way out of either finished state.

**Two pieces outside the blocks.** A workflow's evaluator node belongs to [tillr-item-graphs.md](../reference/tillr-item-graphs.md#workflow-evaluator) and is built there; it hands its file to the same intake. What a worker's obstacle does not yet do is listed in [Section 4.5](#45-what-a-worker-may-end-with-d-jl11).

## 8. Build Order

Fourteen blocks, in the order of [the table above](#7-what-is-built-and-what-is-owed). Each is one run inside one fence. A block's fence includes the copy of the tillr source under `yolo-packs/tillr/`, because every change under `tools/tillr*` is delivered there too. Most blocks keep their heading and a summary of what they build; the finished-state block also keeps its decisions.

### Prevent a gate pass from retiring an owner's criterion

Each criterion has a class, an author states it in the item's own block, and both the store and the loop's verdict step respect it: a criterion marked as the owner's is retired by a person and by nothing else.

### Hold an item that still owes an owner's ruling

The store knows which criteria are the owner's, so the planner does not spend on items that cannot finish. An item whose only unmet criterion is an owner's ruling gains nothing from a worker: the run would end, the gate would pass, and the item would still be waiting for the owner. The planner holds such an item with `owner-only-owed` before any lane is leased (`tools/tillr-drain/drain/plan.go`), and the waiting face names the owner and the owed criterion (`tools/tillr-view/waiting.go`).


### Prevent a failed landing from freezing the item's criteria

A landing that did not take is recorded against the run like a failed gate, and the item's criteria are left alone.

### Add the waiter and reason to every blocked item

A move to blocked stores who the item waits on and why, and remembers the state the item was in so that unblocking restores it.

### Prevent landed and resolved states without their evidence

An item's two "finished" states are claims about the world. `landed` claims this item's work is on the trunk, and `resolved-elsewhere` claims something else satisfied it. The store asks for the evidence: a landing record and finished criteria for the first, a pointer to the other path for the second.

Both states are final, with one exception. When the full suite proves a landing broke the trunk, tillr reverts that landing, and the claim `landed` makes is no longer true: the work is off the trunk. The owner-ruled revert design in [tillr-graph-is-the-path.md](https://github.com/mschulkind-oss/tillr/blob/main/docs/design/tillr-graph-is-the-path.md) says the item "gets its work back" and "lands again", so the loop moves it from `landed` to `in-queue` through the state command, with a reason and the name of who moved it (`ReturnLanded` in `tools/tillr-drain/drain/heavy_revert.go`, tested by `TestRevertedLandingReturnsToTheQueueWithAReceipt` in `tools/tillr-item/terminal_state_test.go`). Every other move out of a finished state is refused.

**A reverted landing is not evidence.** A landing that was reverted proves nothing about the trunk, so only a landing record written after the item's latest return from `landed` counts. Without that, a returned item could be marked `landed` again on the strength of the landing that was undone.

**A test that reaches a finished state gives its fixture the evidence.** A test that needs an item in `landed` or `resolved-elsewhere` in order to assert what happens afterwards records the verdicts, inserts the landing record or passes `--resolves-via` in its setup. Its assertions stay, and no test is deleted to make room for a refusal.


**Where the rules apply.** They apply to a store under the Git-landing definition, which is where `state-terminal` already applies. They cover every write that changes a stored item's state to `landed` or `resolved-elsewhere`: `tillr item state`, the library calls behind it that the loop also makes directly (`SetState` and `SetStateWithReceipt` in `tools/tillr-item/item/state.go`), and `tillr item apply` when its record changes the state of an item the store already holds. A record that creates an item already in a finished state is an import and is still accepted. Imported stores and most test fixtures are created that way, and the fifth criterion depends on it.

**What a landing record is, to the item store.** The `landings` table is created by the lander's schema (`tools/tillr-land/land/schema.go`), and a store that only the item utility has written has no such table. That store holds no landing record, so the move to `landed` is refused as `landed-receipt-missing`; it is not an internal error. The close command already probes for the table this way (`Close` in `tools/tillr-item/item/lifecycle.go`). A test in `tools/tillr-item` creates the table itself with the columns the check reads, `item_id`, `result` and `event_seq`, and inserts the row; `lifecycle_test.go` creates a smaller one the same way for the close command. "Written after" compares event sequence numbers: the lander stores the sequence number of the landing's own event in the row's `event_seq`, and the record is current when that number is greater than the sequence number of the item's latest `item.update` event that took it from `landed` to `in-queue`.

**An item whose graph ends without a commit.** A workflow can declare that its item finishes with no commit (`requires_candidate: no_commit`). The loop moves such an item to `landed` although nothing landed (`completeGraphWithoutCommit` in `tools/tillr-drain/drain/workflow_exit_record.go`), so it has no landing record and never will. Before that move the loop records the criteria as `done` and appends a `drain.graph-completed` event that names the item. That event is this item's receipt: it is accepted in place of a landing record, under the same "current" rule. This is the designer's decision, and the owner may overturn it. The alternative is a different finished state for these items, which changes what every view shows for every such item and is larger than this block.

**The loop's other writes of a finished state.** The fence includes `tools/tillr-drain/`, because a rule that lands without its callers stops the drain. There are three other writers.

- A landed candidate (`completeItem` in `tools/tillr-drain/drain/workflow_exit.go` and `recordLandedJudge` in `tools/tillr-drain/drain/judge.go`). The lander has written the landing record and the verdicts are recorded before the move, so the move passes and the code does not change. A refused move fails the step, as any move that does not take does.
- A change the trunk already carries (`resolveElsewhere` in `tools/tillr-drain/drain/terminal_item.go`). It passes `commit:<sha>` with the candidate's head, a reason and the loop's own name as the actor. When that move is refused as `already-landed`, an earlier landing of this item was recorded and its state move was lost, so the loop moves the item to `landed` instead.
- A trunk fixer resolved by a passing check (`tools/tillr-drain/drain/fixer_resolve.go` and `fixer_rebase.go`). Both already pass a `commit:` pointer and do not change for this receipt rule (under [`D-JL16`](#49-keeping-a-live-trunk-fixers-work-when-a-rerun-passes-d-jl16), a live fixer whose check passes on a rerun finishes first and lands any commit it produces before falling back to `resolved-elsewhere`).

The fence also includes `tools/tillr-land/`, `tools/tillr-loop/` and `tools/tillr-view/`, for test fixtures only: `tools/tillr-land/lifecycle_test.go` moves an item to `resolved-elsewhere` with no pointer, and any other test in those modules that the new refusals break gets the same fixture change.


### Add commands to close an item and reopen it

`tillr item close` records why an item was closed, who closed it and the state it was in; `tillr item reopen` restores that state; the lander refuses work for a closed item; and an item that has landed cannot be closed.

### Move AutoQA onto the ordinary verdict kinds

The store's AutoQA actor kind, claim class and decider are refused on new writes, and stored records that carry them stay readable.

### Add the verdict's author to the item page

The item page shows who recorded each verdict, and raises the one alarm the state model asks for: an item waiting on something that has been closed.

### Add one intake for a judge's written verdicts

One command checks a judge's file before any of it becomes a record: that it covers every criterion, read the text the store holds, looked at the candidate it claims to, and cites evidence. The caller states who the judge was; the file is never trusted to.

### Route an opted-in item through a judge before the gate

An item that asks for a judge in its own block is judged after the worker commits and before the gate. The judge reads and never writes, and its rulings are recorded only after the landing.

### Route a judge's blocked and defective findings to their states

A judge's blocked finding moves the item to blocked, waiting on the waiter the judge named. A defective finding is recorded, and the item is closed with the judge's reason.

### Route a second failed attempt to the design seat

Withdrawn by [`D-JL10`](#44-how-a-worker-runs-ending-moves-its-item-d-jl10). A failure tally does not trigger escalation: only an identical repeat goes to the design seat.

### Prevent cloning a held item under a new id

`tillr item sync` refuses a copy of a held item filed under a new id.

### Route design gate refusals back to the same session

When the repo gate refuses a design commit, the designer needs the failing checks and their output to repair it. Starting a fresh design session for that repair forces another designer to reread the documents and reconstruct reasoning that may never have been written down. The owner ruled on 2026-11-17 that this refusal is feedback, not a failed design run. It returns to the session that wrote the commit so the designer can continue with the context already in hand.

This connects the submission-and-response flow with the ability to resume a finished worker's session, applying both to the design seat. Each revised commit goes through the same allowed-path checks and repo gate as any other design answer. Every refusal is returned without a retry limit; only an objection that names the owner reaches the owner. If a design run is killed, its recorded session is resumed when it is still available. If that session is gone, a fresh one starts and the conflict text explains that choice.

- **Outcomes:**
  - Return each gate refusal to the original designer session and check its revised commit before landing it and answering the conflict.
  - Resume interrupted design work when its session remains available, or explain why a fresh session was needed.
  - Continue repairs without a retry limit and send only objections naming the owner to the owner.
